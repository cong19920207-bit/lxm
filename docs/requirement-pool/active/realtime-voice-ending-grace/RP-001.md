### [RP-001] 收尾审核不可用后的对话体验与宽限期（待评估）

- **涉及入口**：`WebSocket /api/voice/calls/{call_id}/stream`、`GET /api/voice/calls/{call_id}`；主要涉及 `backend/services/realtime_voice_gateway_service.py` 的收发与等待状态、`backend/services/realtime_voice_ending_service.py` 的收尾审核与结束策略。
- **用户场景**：角色在通话时长将尽时提示要结束，用户继续回应；用户话语已被识别，但角色持续无声，随后以“听不到你”为由结束。用户预期在收尾阶段获得可理解的回应，且额度归零后的宽限期按确认的产品规则运作。
- **观察依据**：2026-09-27 本地 Docker 样本中，低余额提示后的多轮用户语音有 ASR 记录；日志连续出现 `voice.ending.semantic_unavailable` 与 `voice.ending.new_topic_or_unverified_rejected`。额度归零后，记录到约 4 秒宽限即以 `silence_timeout` 结束。
  样本与“上行仍通、下行回复被拦截、静默结束先于宽限截止”的代码路径一致；统一的 `semantic_unavailable` 日志无法区分具体底层原因。本条不保存账号、通话 ID 或私人转写。
- **当前实现**：`time_low` 默认在余额剩余 60 秒时触发；额度归零后默认有 30 秒宽限。进入 `soft_closing` 后，候选回复先缓存至完整文本；除服务端绑定且全文精确匹配的固定告别语外，通常需经语义审核才下发。审核不可用会使候选音频不下发，网关随后将 `waiting_user` 置为 `True`。静默计时依赖等待状态与麦克风状态，因此回复受阻可能表现为用户“沉默”。
  现有固定文案兜底仅覆盖已进入 `silence_timeout` 告别的部分场景。以上是现状描述，不构成对 PRD 要求的判定。
- **候选优化方案**：
  1. 区分审核明确拒绝与审核不可用，并记录不含对话原文的原因类别，例如披露守卫拒绝、超时/请求异常和返回格式错误；继续拦截未经许可的新话题音频。
  2. 将“助手回复尚未播出或被拦截”与“正在等待用户说话”分开表示。审核不可用本身不应被当成用户静默；用户再次说话应更新静默判定依据。
  3. 在低余额与宽限阶段评估有界恢复方式，例如有限重试、服务端绑定且完整匹配的固定收尾语，或清晰的失败反馈；不得直接放行未审核的候选音频。
  4. 核对用户明确告别、真实静默、额度耗尽、`hard_limit` 与审核不可用并发时的结束优先级、提示文案和结算口径，再确定实现方案。
- **待确认**：如有现行实时语音 PRD/契约，核对其中对“即将结束”提示、30 秒宽限、用户继续说话及静默结束的要求；若尚无对应契约，先明确产品口径。还需确认宽限是否保证可继续对话、哪些情况允许提前结束，以及审核不可用时应给用户何种反馈。当前 manifest 未登记语音接口契约，不能把本条候选方案当作已确认需求。
- **验收草案**：覆盖连续审核不可用且用户持续说话、真实静默、用户恢复说话、明确拒绝新话题、固定文案不完全匹配、额度归零后的宽限截止、`hard_limit` 和重复结束；确认用户已被识别时不会无依据地听到“听不到你”，同时不扩大未审核音频的放行范围。
- **排期状态**：待评估；可在后续实时语音收尾体验与可靠性迭代时讨论，扩大试用范围前重新核对。
- **影响评估**：当前样本为用户可见的连续无回复与提前结束；具体优先级及方案需产品和技术共同确认。
