### [RP-003] 区分多次经历保留与当前事实更新

**本期决定**：用户在记忆写入与混合召回优化讨论中明确选择“不扩大修改范围，但是可以记录一个需求问题”。本期保留现有 Stable Key、doc_id 和同 Key 覆盖规则；不新增事件身份、事实版本历史或历史对话重抽取。收录本条不授权开发或处理生产数据。

**问题与证据**：当前 `build_doc_id` 由记忆类型、Stable Key 的哈希和用户归属构成；同一身份执行 upsert 会覆盖原文档。文字 Step6 的输入没有对应的已存长期记忆，但默认提示词要求合并新旧 value，因此无法保证保全同 Key 的旧内容。依据：[doc_id 构造](../../../../backend/utils/character_knowledge_validate.py)、[Step6 提取与写入](../../../../backend/services/memory_llm_service.py)。这是静态代码确认的能力限制，本次没有检查线上数据，不能据此断言某条真实经历已被覆盖。

**示例**：用户分别描述两次日本旅行，如果提取成同一个 Key，较后写入可能覆盖较早经历；而“当前居住城市”又可能需要更新为最新状态。两者需要不同的保存语义，不能只靠更换 BM25 或 rerank 解决。

**后续待评估**：如何区分当前事实与独立经历；同一经历补充、用户纠正和多次发生如何判定；身份、时间和来源如何表示；历史数据如何处理；后台编辑、删除及各写入入口如何兼容。事件 ID、追加保存、版本化等仅是候选方向，尚未选定。

**验收场景草案**：两次独立旅行可以分别召回；同一旅行补充不会错误生成另一事件；明确更新当前居住城市后，日常回答使用当前事实；缺少时间或来源时不伪造；后台编辑、删除的作用范围清楚。具体规则留待本需求评审。

**本期影响说明**：混合召回和重排只能改善现存内容的查找与排序，不能恢复已经被覆盖且没有其他来源保存的经历。历史 BM25 回填只为现有正文建立索引，不等于历史事实恢复。
