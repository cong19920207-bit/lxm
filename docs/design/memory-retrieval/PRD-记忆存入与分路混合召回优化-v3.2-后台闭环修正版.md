### 6.2 目标主流程

```text
存入（记忆正文与提取结构沿用现有实现）
├─ 文字 Step6 四类 / 语音两类 / Admin 既有新增更新
│  └─ 现有 doc_id、正文、类型与归属

│     └─ value → BM25 索引（后端实现待 §9.3）

└─ 新库现存正文 → 完整回填、核对、失败恢复（不搬迁旧Cosine）

文字查询
├─ Step1 原有上下文准备
├─ Step1.5（本阶段最多 45 秒）保留四路字段，Keywords 替换为 BM25 检索词组
│  ├─ Question：完整语义，供向量召回与本路 rerank
│  └─ Keywords：本路 BM25 检索词组；不新增统一 Query
└─ Step2（整个阶段另最多 45 秒，四路共用截止时间）对每个启用路分别执行
   ├─ 有效 Question → 本路向量候选上限 → 向量召回
   ├─ 有效 Keywords（缺失/为空时用 Question）→ 本路 BM25 候选上限 → BM25 召回
   ├─ 本路候选按文档身份去重，保留两种来源
   ├─ 本路 Question + 本路候选 → 本路 rerank/相关性准入；失败按名次融合
   └─ 四份有序结果 → Step3 分类型消费
      ├─ 前三路 → 既有角色设定与知识模块
      ├─ user → 既有用户记忆模块
      └─ 按四项最终数量、模块和总预算选入 → 预算合格才进入 Step5 及后续链
```

不存在四路合并 rerank 或跨请求分数统一淘汰。两个阶段各自预算包含重试和退避，故障细节见 §7；语音读取升级已延期，边界见 §6.4。

### 6.3 查询、分数与预算规则

- **已确认原则**：四路保留；原有无需检索的路可跳过；新召回中的分类硬过滤移除，但 Stable Key、key_l1/key_l2 数据和管理展示保留。user/private 的用户隔离不能被 BM25 或 rerank 绕过。
- **已确认词组规范（S5）**：本文“BM25 形式”指 Step1.5 输出适合 BM25 字面匹配的检索词组，并替换原 Keywords 内容。Question 保留完整语义，供向量与本路重排。LLM 不生成 BM25 权重、词项 ID 或稀疏向量；分词与编码仍由检索组件执行，详见 §6.5。
- **索引口径（RQ-13）**：新写入、更新和历史回填的 BM25 均仅索引现有 value，不拼入 Key/分类字段；保留 content 的 `key：value` 展示格式、身份及元数据。当前向量主写入也只编码 value，Key 仍用于 doc_id 和同 Key 覆盖。
- **兼容实施说明**：保留 Step1.5 既有字段结构，只停止新 Step2 对 CandidateKeys 的硬过滤消费，不删除其他消费者所需的共享过滤能力。内部结果须表达路、文档身份、路内名次、候选来源及原分、可空的重排分、排序方式和降级原因；具体字段名在技术方案确定，不新增公开客户端字段。
- **相关性（RQ-12）**：正常路径由 rerank 排序，每条候选达到可配置的最低相关性门槛才可选入，允许整路为空；具体数值经评测确定。只改写降级但 rerank 成功时仍判分；rerank 失败用名次融合，不套重排门槛，不把向量/BM25 原分或融合分伪造为重排分。相关性不是事实真假概率，情绪/ASR confidence 保持独立。
- **数量（RQ-05/RQ-19）**：四路各自配置向量候选上限与 BM25 候选上限，共 8 项；另有四路最终注入上限，共 4 项。候选先在路内合并去重，再重排和准入；最终受本路数量与 token 预算双重限制，不按跨路分数竞争名额。
- **旧配置过渡（RQ-06/RQ-23 A，S14修订）**：主文字/OpenAPI/Step8 接入新链后，停用旧统一 TopK 控件和新链对 `vector_retrieval_config.top_k` 的读取，历史版本仅供审计；旧值不自动复制为四路最终上限。新链不加向量或 BM25 候选分数门槛，各通道按独立上限召回；正常最终准入用 rerank 门槛，故障按名次融合。所有现用消费者按归一化 DotProduct（越大越相似）适配，语音/Agent 自身数量和业务筛选须单独验证，不沿用 Cosine 距离方向或混入 rerank 分；不维护旧度量运行分支。
- **模块预算（RQ-07）**：保留角色三路共享预算与 user 独立预算；角色按公开设定→私有信息→角色知识的路内 rank 轮转取第 1 条、第 2 条……，空路跳过，不跨路比分。计入完整渲染条目及标题/标签/分隔符，不保证 token 均分或每路至少一条，接受紧预算下固定顺序偏向。
- **整条选择（RQ-08）**：某路下一条完整记忆放不下，停止该路，当前条及后续均不选；角色其他路继续轮转，user 同样保留路内排名前缀。禁止截断记忆正文，接受预算余量未用尽或某路无注入。
- **总预算（RQ-09）**：沿既有模块裁剪优先级，以完整已选记忆为单位继续裁剪；不得重新跨路比分或从完整候选列表补回已淘汰项，各路仍保持排名前缀。角色模块内的移除顺序按 §6.3.1 已细化的成功选入逆序执行并记录，Q03 只落实计数/参数及接口，不重新选择跨路排序。最终仍超当前生效的约定总预算时，不调用回复模型，沿 §7.3 接入既有失败反馈，不自动换用另一套预算配置。后台提前校验不合理配置；计数器/预留量待 §9.3，不将近似计数冒充模型实际 token。
- **有效配置一致性（F09）**：每次业务检索或诊断冻结实际使用的检索、预算、模型及索引编码版本组合；后续阶段复用该组合，期间发布只影响后续请求。版本来自实际消费值，不能运行结束后读取新版本替当时结果作证；缺失/非法配置的技术回退必须显式记录来源，不冒称已发布版本。

#### 6.3.1 最终选入与结果保真（v3 既有细化 D；R04/R05）

Step2 输出和 Step3 选择结果保持文档身份，不能在合并角色三路时丢失 `doc_id`/route 后再按分数重建。正常重排、故障融合、模块初选、总预算二次裁剪及最终有效性检查，均从同一组候选及冻结配置推导，不由诊断页另算一份。

| 内部结果层 | 最少保留的语义 | 消费约束 |
|---|---|---|
| 通道候选 | route、doc_id、type/归属、正文及其可信代次/摘要、通道、通道原名次/原分、检索状态 | 不跨用户/类型去重；原始分不改名为 rerank 分；源请求失败与正常空结果可区分 |
| 路内排序 | 合法去重正文、输入索引映射、路内 rank、可空 rerank 分、排序方式、门槛准入/降级原因 | 同分按固定输入顺序，再按稳定身份收口；不跨路比分；具体融合公式仍由 Q04 定稿 |
| Prompt 构建结果 | 完整 Prompt（仅运行时）、模块初选和最终选入清单、最终渲染条目、计数器/预算版本、初选/二次裁剪/有效性淘汰原因 | 业务请求直接消费该 Prompt；诊断消费同次构建的清单，不解析字符串猜选入 ID，不在结束后读取新配置重算 |

重排正文口径在本轮统一为现存 value；可靠历史自由文本沿 §6.6 取完整 content。Prompt 展示沿现有 `key：value` 及角色标签，不把 Key 拼进 BM25/embedding，不改库中正文。标题、标签、分隔符及请求封装的预算归属须在 Q03 明确；诊断 token 标明计数器版本，不将近似值叫作供应商实测 token。

总预算二次裁剪必须从已选集合移除各路尾部，保留各路前缀；角色模块采用**本次轮转成功选入顺序的逆序移除**，不比较跨路分数、不从候选库补位。这只是 Q03 中确定性移除顺序的技术细化，既有模块裁剪优先级与轮转初选策略不变。最终有效性检查若使已选前缀中的条目失效，同路该条及后续已选项一并淘汰，重新计数，不补位；记录淘汰原因，不能沿用先前“已注入”记录。

共享 helper 必须区分新链和范围外消费者：普通 Agent 的旧记忆构建行为保持；不能为了新链全量替换公共排序/截断函数而无意升级普通 Agent。正常聊天只保留运行所需结果，不因此新增每句完整检索快照或完整 Prompt 永久留存。

#### 6.3.2 Prompt 预算保存与固定字段（RV31-R01）

`user_nickname` 沿已有代码保留固定预算配置值 **50 token**，不是新增热配置项。该常量不证明昵称文本有50-token硬上限：当前构建器明确不裁剪昵称；本期保持这一行为，实际全文参与总预算计数。修正 `/api/admin/configs/prompt_token_config` 时，必须区分“可编辑配置集合”和“运行时完整预算集合”：

1. GET/PUT 的可编辑字段以现有 `_prompt_hot_config_keys()` 或等价单一白名单为准；可编辑值合并与合法性校验遍历同一集合。不得因为请求没有 `user_nickname` 就按 0 拒绝合法更新，也不得为绕过错误把它开放编辑。
2. 部分更新以已确认生效配置为基底；没有历史配置时采用同一版本的合法默认配置，保留未提交字段。空更新、未知字段、非法类型/范围及主动提交固定字段，继续按既有拒绝边界处理。不得“保存成功”后悄悄恢复旧值。
3. 固定预算配置值50在运行时配置中保留；最终完整Prompt的实际昵称文本及封装按同一定稿计数器完整计入总量。昵称实际超过50而完整输入不超过max_total时保持可用，不按50裁剪或单独拒绝；经原定裁剪后完整输入仍超max_total时按RQ-09阻断回复调用。不得把50当实际占用或额外额度，也不能把模块配置值之和冒充实际Token。`memory`、`character_knowledge` 与 `max_total` 的实际值仍按 Q03 定稿，固定字段修复不调整这些值。
4. 配置完成提交后，GET、后续业务请求、诊断应消费同一有效值/版本；提交或发布失败不暴露半套生效配置。在途请求保留原冻结预算，只有后续请求消费新值。

STEP-003交付校验修复和正向保存测试，不能只测非法值被拒；STEP-002登记昵称全文计数边界，STEP-013执行超过50但总量合格/最终仍超总量的构建断言（AC12-a/AC26）。固定值来源是既有代码基线；current契约的“上限50”在本节解释为固定配置常量，不视为已实现文本硬限制，本轮未改运行契约。

保留 `POST /api/admin/prompt/test` 的原用途、鉴权、请求/响应信封、当前配置/草稿模式及受控系统提示覆盖。它仍是使用 mock 记忆并可调用回复模型的旧测试工具；新“记忆检索诊断”仍运行真实检索但止于实际选入，两者不能合并或互相代替。

### 6.5 Step1.5 BM25 检索词组规范（F15）

**✅ 已确认（S5/RQ-10）**：调整查询改写 Prompt 中各路 Keywords 的生成目标与输出内容，替换原来用于补充向量搜索的词组。保留四路各自的问题，不增加词组补齐专用 LLM 调用，不调整 Step6 记忆正文或拆解方式；临时调用故障的有限重试另按 §7.2。这里的“BM25 形式”是检索词组文本，不是新的算法数据结构。

| 路 | Question 职责 | 替换内容的既有 Keywords 字段 |
|---|---|---|
| 角色公开设定 | 本路完整问题，供向量及 rerank | `CharacterGlobalQueryKeywords` |
| 角色私有信息 | 本路完整问题，供向量及 rerank | `CharacterPrivateQueryKeywords` |
| 角色知识 | 本路完整问题，供向量及 rerank | `CharacterKnowledgeQueryKeywords` |
| 用户记忆 | 本路完整问题，供向量及 rerank | `UserProfileQueryKeywords` |

输出沿用字符串，以空格分隔检索词组；不改成数组或数值对象。根据 S5 所确认的词组优化讨论，生成规则为：

1. 保留本路问题中的原词及有依据的人名、地点、物品名、主题词和必要限定词；只用已有上下文消解指代。
2. 去掉“你还记得”“事情么”等提问套话和无助于字面匹配的重复词；避免只剩“经历、事情”等宽泛词。
3. 可以少量补充含义明确的同义词，如“旅游、旅行”；不以扩词为由添加未提供的城市、年份、人物或活动，也不为增加权重重复堆词。具体扩词数量不编造固定门槛，效果按 Q05 评测。
4. 完整的否定、时间关系、主体和条件仍保留在 Question 中，不能只靠关键词承担语义判断；Keywords 不得把否定或不确定表述改造成相反的实体条件。
5. 向量与 rerank 使用本路 Question；BM25 使用本路新 Keywords，替换旧“Keywords 再做补充向量”的职责。分词、词项权重及稀疏编码由查询组件与文档索引匹配的编码器处理；文本词组不自动等同于精确短语匹配。
6. 有效输出明确“无”或合法空 Question 的路跳过；缺字段造成的默认空值不是明确跳过。启用路 Keywords 缺失/为空时直接使用有效 Question 文本，交查询组件分词编码；其他补齐规则见 §7。

示例：输入“你还记得我们那年去日本旅游的事情么？”，在没有明确年份/城市上下文时，用户记忆一路可输出以下片段（示例不是实际模型结果，也不要求额外写入一条旅行记忆）：

```json
{
  "UserProfileQueryQuestion": "用户提及的过去与林小梦去日本旅游的相关经历",
  "UserProfileQueryKeywords": "日本 旅游 旅行"
}
```

此例允许包含“旅游”或“旅行”等相关词，不以固定字符串作为质量通过标准；不得凭空加入“2023、东京、大阪”。其他路同样围绕自己的 Question 生成词组，不能复制用户路词组代替本路意图。

**配套改动**：同步 Step1.5 Prompt 的字段说明、生成规则和 few-shot 示例；后台主链与 Step8 只读预览展示相同规则，不新增编辑/发布能力。真实诊断应能辨认新 Keywords 进入 BM25、Question 进入向量和本路重排。客户端公开字段无需变化。效果评测比较旧词组、新 BM25 词组及完整 Question 查询，质量门槛仍归 Q05。

### 6.6 索引维护与失败恢复（RQ-14/RQ-14.1）

正文/向量已成功、BM25 失败时，标记“记忆已保存，BM25 索引待修复”，允许成功的向量召回继续使用；不能显示索引完整成功。更新/删除后的过期索引内容不得作为当前有效记忆使用。各来源新增、value 更新、删除及历史回填都需有可核对的结果。

后台维护记录应关联记忆身份、类型/归属、来源及操作，显示当前状态、失败原因、修复尝试和恢复结果。自动补索引采用有限重试，达到次数或等待时限后暂停并标记“需人工处理”，支持后台手动重试。具体次数、间隔及上限在技术方案中定稿；这不是在线检索的 45 秒预算。

修复按当前有效正文与删除状态执行，不重跑提取 LLM、不重放旧值、不复活已删除记忆；一个记录停止重试不妨碍其他记录维护。历史回填须完整遍历、可续跑、协调并发增改删并核对失败项。保持 Step6 在回复之后异步写入的边界，不把本期扩为所有历史任务持久化治理。

**恢复故障窗口验收细化**：源库读取失败不能当作确认不存在或已删除；无法确认当前正文时保留待处理状态。正文成功后进程中断、BM25 调用超时但远端结果未知、维护记录保存失败均须可发现和恢复，不能留下不可追踪缺口。技术方案须定义持久锚点与对账方式，不以“失败后再记一条日志”证明恢复完整。BM25 失败不触发原提取任务重放；语音成功 trace 不充当索引完整成功。

旧修复不得覆盖较新正文；删除与修复并发、同 ID 删除后合法重新创建时，过期操作不得复活旧内容或删除新内容。用于一致性校验的操作代次/正文摘要是技术元数据，不提供事实版本查询或历史恢复。保护范围只覆盖本期派生索引维护，不承诺解决所有跨入口原始写入顺序问题。

**历史正文口径（S15限新库后续维护/隔离样本；旧Cosine不搬迁）**：当前四类新写入保存 `content=key：value`，没有统一独立 value 字段；按已知写入格式核实正文与归属。合法 KV 取现存 value；旧 `mem_*` 自由文本在 type、user_id 和来源可靠时取完整 content 作为正文/value，不因自然语言冒号截掉前文，不生成 Stable Key。按标准 KV、兼容历史正文、空正文及身份/解析异常分组对账；无法可靠识别正文或归属者列入待处理，不改正文、不静默跳过后报全量完成。保留既有 `mem_*` 稠密读取兼容，不借回填自动清理或增加检索过滤。当前列表除 cap 外还存在展示身份过滤，回填不能直接复用列表解析/过滤 helper；格式识别和全量遍历细节由 Q06 定稿。

#### 6.6.1 操作结果及后台反馈（v3 既有细化 D；R02）

“正文保存”与“BM25 索引完整”分开判断；源操作、索引操作及维护记录分别保留结果。判断源操作成功须检查实际接口业务结果，不能只看 HTTP 2xx、单一布尔返回或少量 message 关键词；读取接口也必须区别明确不存在与读取失败。以下是目标语义，增量write_result与自有操作回执目标见§6.8.4/6.8.8；物理字段及错误码由Q06/Q07定稿并兼容现有信封。

| 源正文/向量结果 | BM25 结果 | 对外语义及后续行为 |
|---|---|---|
| 已确认成功 | 已确认同代次完成 | 记忆保存完成、索引维护完成；可见性及有效性仍按 §6.6.2，不能把写请求接受等同于读结果已收敛 |
| 已确认成功 | 失败、处理中或结果未知 | “记忆已保存，BM25 索引待修复”；保留确认有效的向量能力；后台展示维护记录及当前尝试状态，不提示重新新增正文 |
| 明确失败 | 未执行或已产生先行索引 | 不报记忆保存成功；先行索引不得作为有效记忆；记录并清理/修复不匹配派生结果，不影响其他成功条目 |
| 结果未知，例如超时/响应丢失 | 任意 | 标记“结果待核实”，先按操作身份核实，不当作不存在、已删除或完整成功，不盲目重放新增/旧 value |
| 删除已确认且失效标记可靠生效 | 词法清理未完成 | 源记忆已删除、索引清理待修复；新链不得再注入该代次；保留删除维护任务，不能因词法失败复活正文 |
| 批量部分成功 | 混合 | 每条返回或可查对应身份、源结果、索引状态、错误及维护任务关联；整体汇总分别计数，不只返回一个 bool |

已保存但索引失败的 Admin 新增仍按保存成功收口，给索引警告和维护入口；不自动再次提交新增或改变“同 Key 已存在则编辑”的规则。文本 Step6 和语音按既有成功/失败协议处理正文结果，索引部分失败不重跑提取 LLM；每条独立记录并汇总，不把一条失败扩大为全部失败。

恢复任务至少区分待处理、处理中、待重试、需人工处理、完成、被新操作取代；源结果未知与索引失败分列，不能共用一个“失败”掩盖核实动作。手动重试复核当前身份/代次，重复点击不创建并行的同一有效任务；已在执行则返回当前任务，已完成则说明无需重复，已被取代则关联最新任务。重试上限/等待时间及手动重试是否开启新一轮预算由 Q06 明确，不隐含无限重试。

#### 6.6.2 有效性生效点与并发保护（v3 既有细化 D；R01）

本期需要的是派生索引与当前有效正文一致，不是新增事实历史库。对本期接入的写/删入口，以**业务操作已确认且其当前有效代次或删除凭据已可靠登记**作为成功确认点；不能在登记失败后仍对外宣称“删除已生效、旧内容不会再注入”。源操作已发生但登记结果未知时保留可恢复的“待核实”状态，写前锚点/等效机制与对账方式由 Q06 实施，不只在失败后补日志。

新文字/OpenAPI/Step8 链及真实诊断在候选送 rerank 前校验身份与有效性，并在最终选入交给回复模型前核验已选项；已知被替换/已删或无法确认有效的候选，不作为当前有效记忆注入。允许“正文成功、BM25 待修复”的**已确认有效向量候选**继续使用；不是要求等待全部索引完成才可聊天。

每条须有可信当前代次/正文摘要与删除状态的判定依据，不能仅凭可能滞后的同一次 query/fetch 相互证明有效。若同 ID 两通道正文或代次不同，只保留能证明确属当前有效正文的来源；旧版本的命中名次/分数不能挪给新正文。无法证实时排除该候选并记录原因，不伪装为正常无命中。历史条目按 Q06 建立经对账的基线，不要求已存在新字段，不补造事实时间。

技术方案必须给出候选使用与并发变更的确定顺序，以及最终检查到使用之间的保护方式，不能只写“调用前再 fetch 一次”。**成功变更在本次最终使用检查之前生效，旧代次必须排除；检查之后才发生的变更，不追溯撤回已合法交付给模型的历史上下文。** 本期不承诺中途撤回模型输入、删除已生成对话或诊断历史快照；后续请求按新状态处理。校验耗时纳入对应阶段/整轮预算，不增加无界等待；范围外语音/普通 Agent 不自动获得新读侧一致性保证。

原始写入入口间的事实优先顺序仍不在本期解决范围；但接入本期索引维护的每次操作必须可区分。旧任务、回填和索引重建在提交前核对当前代次；失去资格即停止，不覆盖/删除新代次。当前有效性凭据不是可任意删除的已完成历史：删除维护历史不得连带移除仍用于防旧任务复活的保护状态；何时可安全回收由 Q06 证明。

#### 6.6.3 活跃写入包装层的状态传递与验证（RV31 补充）

接入不能止于共享 writer 的单次返回。文字从 `execute_step6` 到 `upsert_step6_vectors`，语音从 `_write_atom` 到 `upsert_user_memory` 及 trace 提交，均须消费 §6.6.1 的源/索引分态。

源保存已确认且索引失败/迟滞时，返回“源成功、索引待修复”的可追踪结果，索引故障不得漏成驱动原提取 pipeline 重试的异常；原关系等无关副作用不因补索引重复执行。源结果未知时先按持久操作身份核实，不误写源成功 trace，也不盲目重抽取。索引恢复使用已保存的当前正文及操作身份，与原提取是否再次运行无关。

语音 writer 外层在评审快照中有既有 **20 秒**等待，本期保持该写入包装层时限，不把两个文字 45 秒或整轮 180 秒套到它。源成功不能以等待 BM25 完整成功作为回传前提；通过已定持久维护锚点让索引异步补齐。外层取消/超时、成功 trace 或进程异常均不能使索引任务丢失，也不能让 trace 被当作 BM25 已完成的证据。这里只约束本期写入状态适配，不改语音内容提取、既有读链时限或全部历史任务可靠性。

STEP-006 必须用故障注入经过实际包装层验证 AC30-a；源明确失败仍沿原失败语义，测试中的源成功/失败/未知与索引状态分别记录。

### 6.7 独立诊断页、权限与记录（RQ-15～RQ-17.1/RQ-21）

新增独立“记忆检索诊断”页面，并关联索引维护记录；页面、接口、回填承接及分入口权限采用§6.8目标规格。管理员主动执行一次诊断，使用与业务一致的有效配置，运行实际改写→向量/BM25→路内 rerank→Prompt 实际选入；展示四路输入、过滤、候选来源/数量/分数、排序方式、实际选入、淘汰/降级原因及耗时。诊断到此结束，不调用回复模型、不触发 Step6；普通聊天每句话自动保存完整快照不在本期范围。

每次诊断明确指定用户、输入及实际链路来源，沿对应业务入口准备人格、关系、近期对话、情绪、时间及输入截断上下文，标明装载来源与时点；不能复用 mock 测试的固定用户或模拟关系，诊断输入不进入聊天队列。最终选入 ID、正文、数量、token 与实际渲染结果一致，同时区分模块预算淘汰和总预算二次淘汰。历史记录用于回看当时结果；重新执行使用当次有效上下文并生成新记录，不声称仅凭输入/候选快照即可精确重放旧结果，不扩大为完整对话/Prompt 留存。

| 操作 | 超级管理员 / AI训练师 | 观察者 | 运营管理员 / 技术运维 |
|---|---|---|---|
| 执行真实诊断、手动索引重试 | 允许 | 不允许 | 不新增权限 |
| 查看诊断及索引维护记录 | 允许 | 允许 | 不新增权限 |
| 手动删除诊断历史/已完成维护记录 | 允许 | 不允许 | 不新增权限 |

权限由后端强制校验，保留用户/类型隔离；不能把运营管理员在用户管理中的局部权限推广到四路诊断。既有其他业务角色权限保持。

每次诊断保存结构化信息及原输入、四路 Question/Keywords、候选正文快照，供回看当时内容；不默认保存全部对话、完整 Prompt 或回复输出。诊断详单/快照与已完成索引维护记录**永久保存、不自动过期，后台手动删除**。删除诊断历史同时删除其文本快照；既有不可删除的操作审计只沿原规则保留操作摘要，不复制被删除的诊断全文。未完成/待人工处理的恢复任务不能作为已完成历史清理，也不能因清理历史而被取消。

**源记忆删除后保留历史诊断快照，直到管理员手动删除诊断记录（RQ-21 B）**；S15启用前旧对话正文副本的一次性清理例外见§12.4。快照标明其历史诊断用途，只供查看，不作为当前记忆参与召回，不作为补索引正文，也不提供事实版本恢复。手动删除诊断历史不会删除当前记忆正文或向量。

#### 6.7.1 页面与操作闭环（v3 既有细化 D；R08）

诊断执行状态与历史保存结果独立展示：执行中、完成、部分降级、执行失败、预算阻断分别显示实际阶段及原因；“运行完成但历史保存失败”不能显示成记录保存成功。执行请求有可关联身份，重复点击同一次提交不重复启动付费调用；显式“重新执行”生成新记录，使用新执行时的有效配置和上下文。执行身份不等于普通聊天 generation。

列表提供分页、时间/用户/来源/状态筛选；索引维护记录另支持类型、操作及记忆身份定位，并能查看最近错误、每次尝试、下次计划或人工处理原因。运行中页面刷新通过执行身份查询状态，不以刷新为由再次执行；进程异常不能无限显示“执行中”，需有可识别的中断/待核实状态及失败反馈，具体持久化与接口由 Q07 定稿。执行并发上限、分页范围及请求等待方式须在上线前配置校验，不新增自动定时全量诊断。

手动重试与历史删除均由后端鉴权且有逐项结果；删除失败保留原记录并反馈失败。未完成/待人工处理的维护任务禁止按“已完成历史”删除；只有纯展示历史可删，仍被恢复/一致性保护引用的状态不得误删。诊断历史删除同时删除附属文本快照，不删除当前记忆、不调用恢复。批量与并发操作必须有确定结果，不能把前端按钮禁用当作权限或幂等保护。

同源上下文装载只复用**读取与输入组装**，不复用有写入副作用的 send/Step1 入口。诊断不得增加用户消息、消耗聊天发送/重发额度、改变 generation、关系/最近互动、情绪、Future、主动计数或触发 Step6；仅允许本期诊断记录和既有操作审计等管理侧必要写入。外部调用仍有费用，需记录实际调用信息，不宣称诊断免费。

#### 6.8.4 记忆新增、编辑、删除与操作回执

批次对每个唯一输入只归入一个源状态，断言：源成功数＋源失败数＋源未知数＋源处理中数＝唯一输入数；索引待修复是其中的独立维度，**不能再加到源结果合计**。示例显示“已删除2条（其中1条索引待清理），失败1条，待核实1条”，不是合计5条。成功项刷新移除，失败/未知项保留可定位结果；重复点确认或整包响应丢失不得重删已成功项。源/索引未知先核实，不能把“重试失败项”偷换为重放整个批次。

#### 6.8.5 真实诊断页与历史详情

PLANNED `admin/pages/memory-diagnostics.html`，在现有“AI对话配置”分组中紧邻“召回与Token”增加“记忆检索诊断”；同组另增“索引维护”。`MENU_CONFIG`、observer菜单生成、当前菜单高亮、页面角色检查及后端鉴权同步，旧菜单不移动或复活已移除的一级“记忆规则”。

诊断输入区为：必填正整数用户ID、链路来源（主文字/OpenAPI/Step8）、输入文本。来源在目标协议中固定为 `main/openapi/step8`；前两者改写实际source映射main，Step8输入解释为future_action且不消费真实Future槽。输入校验/截断沿相应实际业务适配器，页面展示采用的输入范围，不额外创造一套截断参数。用户ID可直接填写，由诊断后端只读核实；**不依赖AI训练师无权访问的用户管理列表，也不开放用户资料浏览权限**。

“执行诊断”显式启动一次付费流程；提交前生成执行请求ID。重复点击同次提交不得多次调用，刷新/回页按执行身份GET查询；“重新执行”使用新请求ID、新有效配置/上下文，并记录来源历史ID，不将历史候选快照作为当前输入。查询/筛选/打开详情均为GET，不触发模型调用。执行中字段冻结，已有历史查看不覆盖另一次在途执行。正常完成、部分降级、失败、预算阻断、异常中断/待核实分别显示，历史保存状态另列：保存中/已保存/保存失败，不能用执行成功掩盖保存失败。

详情分成五块，不保存完整Prompt：①用户ID、输入、来源和执行时间；②本次实际生效版本/输入装载来源；③四路可展开候选表，显示Question/Keywords、渠道、doc_id、正文快照、渠道原名次/原分、可空重排分、排序方式和排除原因；④同次实际选入、模块/最终Token及两次裁剪原因；⑤阶段耗时、调用/费用可用信息、执行与保存状态。正常无命中、无可编码词项、渠道故障和降级不能都显示成“0条”。代码默认、有效配置、本次冻结配置和历史快照分别标识。

列表按时间/用户/来源/状态筛选，默认按创建时间倒序且同时间以ID稳定排序。新管理列表采用现有分页风格，工程目标默认20、合法1～100条/页；这是本版分页规格，不是模型/性能实测结论。输入文本、候选正文和错误用安全文本节点渲染，不插入原始HTML；URL只携带必要标识/筛选，正文不写进URL。

运行中只允许查询，不把“删历史”作为取消执行。终态历史可按§6.7权限手动删除，确认文案“仅删除本次诊断记录及文本快照，不删除当前记忆”；删除失败保留记录，执行/保存结果未知时先核实再删除。保存失败的执行仍可查状态，不伪造不存在的快照；显式重跑不是“补存旧记录”。源记忆已删时历史标注“历史快照，非当前有效记忆”；没有当前核验证据时不凭空标记“源已删除”。

诊断查询等待/轮询如采用自动刷新，必须消费002冻结的有限并发、单次等待和核实窗口，离页/登出停止观察、不重启执行；不能套用新的180秒业务授权或创建无限“执行中”。本节不提供后台取消/强制完成、全聊天快照、自动全量诊断或回复生成按钮。

#### 6.8.6 索引维护页与回填记录承接

PLANNED `admin/pages/memory-index-maintenance.html`，默认“索引任务”，另设“回填批次”；诊断详情和现有CRUD结果区可按权限携带task_id定位，回填清单可按run_id关联，不要求管理员到代码日志里找唯一入口。

索引任务列表字段：任务ID、type/归属用户、doc_id或可靠历史源身份、来源（文字/语音/Admin/回填）、操作、源结果、索引结果、维护状态、尝试次数、最近更新时间、下一次计划/人工原因、允许操作。详情补操作代次/当前是否已被取代、每次尝试时间及受控错误、关联源操作/回填批次；source round/call_id确实存在才展示，不补造关联。正文仅在原权限范围可读，不把索引状态分数当情绪或事实置信度。

| 维护状态 | 页面动作 | 服务端要求 |
|---|---|---|
| 待处理/待重试 | 可查详情；满足当前源可核实条件的授权角色可手动重试 | 领取必须互斥，复用当前有效任务，不并发重放 |
| 处理中 | 禁止再次启动；允许刷新状态 | 重复请求返回当前任务，不能重复付费或续无限预算 |
| 需人工处理 | 展示原因；可修复且当前正文有效时允许手动重试 | 使用Q06冻结的有限新尝试预算；不可确认源时先核实，不强制写入 |
| 已完成 | 可查看；符合历史清理条件才可删除 | 不重新补索引、不删除当前有效性凭据 |
| 已被新操作取代 | 原任务只读；有权限时定位最新任务 | 旧任务不可再次执行，不能回放旧值或删除新代 |
| 源结果待核实/依赖不可读 | 显示待核实，不给“强制成功/强制补写” | 不能以读取失败等同删除，也不重跑提取LLM |

手动重试后展示服务端返回的任务身份/状态，不先乐观置为完成。维护历史的删除只作用于纯展示历史；未完成、人工待处理、仍被恢复/一致性保护引用的记录不可删。后台允许的历史删除不等于运维取消任务。

**回填批次不是另建生产控制台**：只展示由STEP-008实际回填入口产生的持久批次记录/对账结果；页面不新增启动、暂停、强制完成、全量重试按钮，生产运行仍按022独立授权。单条失败索引的手动修复沿前述既有能力，不重新跑全量提取。

每个批次至少包含：run_id、执行模式（隔离演练/实际环境）、来源范围和索引/编码版本、开始/结束/最后更新时间、执行状态和阶段（扫描/建立索引/对账/追平）、基线/高水位、当前续跑游标或其安全摘要、对账截止点、分类计数、未解决项数及报告是否完整。没有可信总量时显示“已扫描N，总量未确定”，不能用300/500条展示cap作分母或画虚假100%。记录中不保存服务凭据。

按标准KV、兼容历史自由正文、空正文、身份/解析异常分别计数；源身份、当前正文摘要/代次、索引结果以及缺失/多余/不一致/待核实/待重试项可分页查看并关联任务。数量计口径由008生成，不由页面扫描拼接：扫描记录数、唯一源身份数、尝试次数不是同一数值；“已处理数”不等于“成功数”。必须有完整遍历终点、身份+正文对账、增量追平证据且未解决项清零，才能显示“已完成（截至某时点/版本）”；异常、未知或未追平仍存在时显示未完成/需处理，不能仅凭脚本退出0或条数相等完成。

批次中断显示已持久的进度与中断状态；重启仍可读取，不需要重新启动回填来恢复页面。续跑若沿同批次，保留身份和检查点；新开批次有新run_id，不覆盖旧结果。该批次完成只证明其截止点，不承诺此后全库始终健康。持久化/对账结果暂不可读时显示“进度暂不可用”，不伪造0条或已完成。

回填摘要作为维护记录沿§6.7永久保存、手动清理；完成且不被活动任务或一致性保护引用时，才可经统一历史删除入口清理展示记录。不能删除运行批次或保护状态；删除单条展示历史也不能破坏运行批次对账，关联历史已清理时显示明确占位，不以404推断源记忆被删。

**依赖责任**：008产出真实批次/逐项记录及可续跑证据；017实现读取投影/筛选/权限；018接页面；019做页面/API/真实记录的集成回归。017可以先按002契约和夹具实现，但AC11-a及其DONE需等008证据；不让008反向依赖017/018，避免执行环。

## 7. 边界、异常与降级

### 7.1 输入补齐与候选处理

| 明确无需检索 | 有效输出明确“无”或合法空 Question 时跳过；缺字段默认空值、空 JSON 等非法输出不当作主动跳过 | RQ-10；AC07 |
| 仅 Keywords 缺失/为空 | 有效 Question 原文保留，直接作为 BM25 查询文本交查询组件编码 | RQ-10；AC07 |
| Question 异常缺失 | 用本次传入改写的原输入作为该路问题；保留有效 Keywords，Keywords 也缺失则用该降级问题 | RQ-10；AC07 |
| 改写整体超时/无法解析/空对象 | 原输入供各路向量、BM25 和 rerank；保留能合法解析的其他路，有效显式跳过的路不补齐 | RQ-10；AC07 |
| 单通道服务失败 | 保留同路另一通道的成功候选并可继续 rerank；不因服务故障替换已经有效的查询文本 | RQ-11/RQ-20；AC08 |
| 无可用候选 | 不请求 rerank、不虚构记忆；故障和正常无命中记录不同，可用其他对话上下文继续 | RQ-11；AC08 |
| rerank 正常但低相关 | 低于有效门槛不选入，允许整路为空；改写降级后 rerank 成功也照常判分，不沿用旧向量 0.7/0.75 | RQ-12；AC09 |
| rerank 超时/非法结果/不可用 | 仅该路按两个召回通道的名次融合；只有一个通道成功则沿其顺序。重排分为空，不套重排门槛；原始分不可直接跨通道混比 | RQ-11/RQ-12；AC09 |
| 索引维护部分失败/回填冲突 | 按 §6.6 记录并修复；成功结果不冒充整体成功；不重放旧值、不复活删除 | RQ-14/RQ-14.1；AC10/11/23 |
| 单条放不下/最终仍超总预算 | 按 §6.3 停止该路、整条裁剪；最终超限不调用回复模型，返回既有失败反馈 | RQ-08/RQ-09；AC06 |
| 越权或不可信候选 | 保留 type/用户归属与后台角色校验，候选正文仅作为数据，不能覆盖系统指令 | RQ-01/RQ-16；AC13 |

主链原输入是本轮传入改写服务的消息文本，Step8 原输入是自身 future_action。输入补齐是确定性文本复用，不增加补齐用 LLM 调用、不创造事实或写入记忆；通道服务失败不能靠“改成原话”恢复不可用服务。

#### 7.1.1 输入、空编码与重排协议细化（v3 既有细化 D；R04）

解析时保留“字段实际存在”的信息：合法字符串 Question 在 trim 后为空或等于“无”才可主动跳过；缺字段、null、非字符串、空 JSON 不借模型默认值变成主动跳过，按 RQ-10 补齐。启用路 Keywords 缺失、null、非字符串、空白或占位“无”均按不可用词组处理，复用有效 Question；只兼容保留但不被新链使用的 CandidateKeys 非法，不得拖垮本路有效 Question/Keywords，记诊断警告即可。

Keywords 文本合法但编码后无有效词项时，不发送无条件/空 sparse 查询，也不偷偷移除 type/user_id；将 BM25 标为“无可编码词项”，保留向量结果。不增加另一轮 LLM/无限换词；与后端错误、正常有词但无匹配分别计数。已返回的无词项占位结果不能伪装成 BM25 命中。

新链停止候选分数门槛须在适配层真正关闭过滤，不能用 `threshold=0` 代替关闭而继续丢弃负分候选；保留后端对自身度量的合法排序和原分，不全局改写旧共享客户端语义。

每路 rerank 请求绑定冻结的候选输入顺序和正文代次，要求返回全部合法输入的排序/分数（显式全量 `top_n` 或模型的等价机制），最终数量由本系统处理，不提前只请求最终 TopN。返回索引须为范围内唯一整数、分数为该 API 支持范围内的有限数值、覆盖完整；空结果、缺项、重复、越界、非法类型/分数、错误信封均判为本路重排不可用，不把半份响应拼成伪成功。返回正文不替换输入权威正文。正常同分采用固定输入顺序及稳定身份排序，不跨路比较。

发布配置需校验候选数、模型文档数及可计算输入限制；运行中还检查实际 Query、单篇正文和全请求 token。超模型限制时不发已知非法请求、不重试；本路按 RQ-11/RQ-12 降级并标明“重排输入超限”。不静默截断正文、不把一篇记忆拆成多个新事实、不拆成多批再比较跨请求重排分。模型限制、token 计数方式和融合公式仍需 Q04/Q05 定稿。

### 7.2 阶段时限与重试（RQ-20 B）

- Step1.5 改写阶段最多 **45 秒**；整个 Step2（embedding、向量/BM25、四路 rerank）另最多 **45 秒**。四路共用 Step2 截止时间，不按路累加；合计检索等待最多约 90 秒，不含回复生成，也不是整轮聊天响应时限。每阶段的实际截止时间取“阶段起点＋45 秒”与原整轮截止时间中的较早者；不得因进入下一阶段重新获得整轮预算。
- 临时故障每个失败调用最多重试一次，成功调用不重跑；重试与退避包含在所在阶段预算内。参数、鉴权、非法改写/重排输出直接按 §7.1 降级，不靠反复调用修复。
- 改写阶段失败或耗尽后，原输入及已有有效字段进入 Step2 自身预算。Step2 为后续重排/本地收口留出时间；剩余预算不足不重试，耗尽后取消未完成调用、忽略迟到结果，不再发该阶段的新请求。
- 已重排成功的路仍按门槛准入；只有候选而重排未完成的路按名次融合；无候选则本路为空。所有路径继续遵守最终数量、用户隔离及 token 预算。
- 主文字/OpenAPI/Step8 共用链适用以上规则；不套到语音读取或回复模型，不修改其他共享调用方的默认重试。实现需避免外层重试与底层既有重试叠加；单次 HTTP timeout 不能替代阶段总截止时间。

现有服务端/H5 等待均为 120 秒，恢复 bundle 锁 TTL 为 90 秒；仓库 Nginx `/api/` 的 `proxy_read_timeout` 已为 300 秒，应核验实际部署而非把所有层都称作 120 秒。检索之后仍有 Step5、安全检查与可选 Step5.5。现行契约中请求等待超时与后台执行未绑定整轮截止时间，这是已有风险。**RQ-22 已确认 A，并由 S10 定稿整轮数值**：随 v3 将完整回复链业务总预算固定为 **180 秒**，不自动延长；H5/OpenAPI 等待按该预算及必要收口余量衔接。保留 RQ-20 的两阶段各 45 秒。**RQ-24 已确认 A**：仅连接断开不取消已合法入队任务，也不重置其原截止时间，具体状态见 §7.4。整轮 180 秒已经确认；各调用/退避上界、收口预留和各层连接等待余量仍由 Q05 技术定稿；不把约 90 秒当作整轮响应承诺，不改语音读链时限。

完整回复链截止时间耗尽时，尚未合法提交成功的有效本代进入失败终态，取消或忽略未完成调用，不允许之后首次提交成功回复或触发 Step6；失败/刷新/重发沿 §7.3/AC26。已在截止前完成成功提交、但响应传输迟到的任务仍为成功，不能被超时处理覆写为失败；数据库提交结果未知先核实，不能依据连接异常判断尚未提交。generation 作废只影响尚未完成的旧代，旧任务不得改变新代。客户端单独断开采用 §7.4 的继续执行规则，不再作为 Q05 的产品待决项。

### 7.3 总预算阻断后的既有失败链（RQ-09/F11/F12 验收细化）

主文字/OpenAPI 在回复模型前确认超总预算后，结束该代请求并将参与消息标为既有可重发失败态；刷新后状态仍一致，预算修正后的重发不新增重复 user 行。不得只返回 failed 而留在 pending_llm；已作废的 generation 不得标记或唤醒新一代请求。沿既有错误信封/SSE 字段，不新增回复策略；不调用 Step5/5.5，不落成功 assistant、不触发 Step6。

Step8 同类阻断返回失败，Future Handler 保留“失败后清空已消费槽位”的业务，但只清理**本次消费且当前仍匹配的槽位**。执行期间出现新 Future 时，旧任务失败不得清空新槽位；按消费身份/代次条件清理，不能仅按 user_id 无条件清空。失败不生成 agent_message、不触发 Step6、不计本次成功主动消息；不增加自动重试、不顺带重构 Future 业务。独立诊断展示预算阻断及最终选入，不调用回复模型，不修改消息/Future。

### 7.4 客户端断开、截止时间与唯一终态（RQ-24 A；v3 既有细化 D；R06/R07）

**用户决定**：用户离开聊天页或连接因网络中断时，服务端已完成合法入队并保存用户消息的任务继续执行，仍受其原定整轮超时和新输入作废规则约束。客户端断开不等于撤回；本期不增加推送、停止按钮、跨服务完整任务平台或语音断开新规则。未通过入口校验、尚未成功入队的输入不保证已启动任务；客户端不知道是否提交成功时，以 §7.4.1 本期补齐的提交身份与只读核实协议查询，不依据“标识已经发送”推定当前代码已有幂等，不直接重发新增。

| 事件/服务端状态 | 服务端处理 | 客户端及后续状态 |
|---|---|---|
| 仅 H5 页面离开、SSE/HTTP 断开 | 取消连接等待/发送即可，不取消或标失败已接收任务，不因连接 Future 取消而取消业务执行 | 本地可提示连接中断/重新同步；回来后读取服务端消息状态，不当作服务端失败，不自动 send/resend |
| 断开期间成功提交，用户尚未返回 | 保留一次成功提交；后置 Step6 仍仅在既有成功边界内触发 | 返回后读取已保存回复及消息状态，不补发重复回复，不要求用户重发；不承诺恢复已中断的流或主动推送 |
| 返回时任务仍未完成 | 同一有效代继续在剩余预算内执行 | 先同步 pending，再按 §7.4.2 有限持续读取直至终态或待核实收口；不因重进页面创建新 generation/重置 deadline；更新现有消息行，不依赖历史分页追加 |
| 有效本代整轮超限/预算阻断/明确失败 | 原子争取失败终态并持久标记既有失败态，阻止后续成功提交 | 按既有失败类型展示，只有服务端允许的失败窗口可重发；重发沿既有入口、不新增重复 user 行 |
| 新的合法输入使旧 generation 作废 | 旧代停止提交/状态改写；只在既有规则下为新代处理有效未闭环输入 | 丢弃旧 SSE 片段；不撤销此前已合法提交的回复，也不让旧失败覆盖新 pending/success |
| 已成功提交但连接响应丢失，或提交确认未知 | 已成功保持成功；未知需核实提交结果，禁止另起重复成功/失败覆盖 | 通过服务端状态收敛；无法确定时显示待同步，不让前端猜测触发重复生成 |

**整轮计时口径（S10）**：新有效 generation 合法入队时记录起点，原截止时间固定为该起点后 **180 秒**，包含后续防抖/排队、上下文读取、Step1.5/2、Prompt 校验、Step5、安全/Step5.5和结果提交。相同 generation 的恢复、重连和重试继承原起点，不刷新预算；新合法输入按既有机制产生新 generation。Step8 同样使用固定 180 秒业务总预算，从该次子链执行被接收时起算。Step6 异步提取和索引后台恢复不计入回复等待，不因此获得无限重试。

Q05 必须落实一套可证明的“成功/失败/作废”提交仲裁：generation 校验、是否超限与成功事务提交需协调；不能在模型调用前检查一次就默认提交时仍有效。连接等待方注销/超时只能释放自身等待关系，不能清掉仍被有效任务使用的状态。成功提交与 deadline 竞争、数据库响应丢失及崩溃均要可核对；不能用“先发起 commit”代替确认提交成功，也不能因提交结果未知另放行重复重发。具体协调实现与异常状态恢复仍由 Q05 定稿，不声称既有 create_task 已满足。 数据库不可用或提交回执丢失时，不承诺页面立即知道终态；须在恢复后按真实提交结果收敛，并为持续待核实状态提供有界核实/告警处理，不能无限保持虚假的正常执行中。结果核实不延长模型执行权限，也不允许超限后首次生成成功。断线继续不等于承诺进程重启后自动接续原模型流，仍不得扩为全部历史异步任务可靠性治理。

恢复锁使用持有者标识或等效所有权保护：按本代剩余生命周期设计持有/续期；仅当前持有者能续期/释放，旧持有者迟到不能删除后来获取的锁。锁丢失后不得继续无条件提交。不能只把 90 秒常量调大；同代的 deadline、唯一提交保护与重复恢复判定同时生效。

整轮业务预算固定 180 秒。服务端等待覆盖实际入队至终态收口，受控 H5 等待与网关保留必要的状态收口及结果传输余量；这些余量不延长业务执行截止时间。第三方 OpenAPI 调用方的本地 timeout 不受本项目控制，更新接入说明而不保证对方同步修改。较早断开的第三方请求仍不自动取消已入队任务；不新增自动回调或推送。各层连接等待/收口余量的具体数值，以及对应超时是总时长还是空闲时长，由 Q05 标明并在部署环境验证，不将已确认的 180 秒业务预算继续列为待定。

#### 7.4.1 提交身份、幂等与只读核实协议（RV31-R02）

本节定义本修正版采用的目标协议（`PLANNED`），不是已有线上能力。只补齐现有 send/resend 的提交关联与状态读取；不增加自动重发、回调、推送或新的记忆/意图路由。STEP-002 将以下语义落实为经项目现行信封核对的 schema、错误映射、事务时序与参数表，STEP-014 实现，STEP-016 消费。

**身份与兼容入口**

| 入口 | 本期目标输入/能力 | 兼容规则 |
|---|---|---|
| H5 `POST /api/chat/send` | 消费既有 `client_message_id`，作为本次 send 的 `request_id` | 受控 H5 在首次网络提交前生成并保留该标识；沿用既有字段校验，不改变正文协议 |
| H5 `POST /api/chat/resend` | 消费既有 `client_resend_id`，关联本次 resend 及原允许重发的消息 | 同一次传输核实复用标识；只有服务端允许的显式新 resend 才生成新标识，不新增 user 行 |
| OpenAPI 原 send/resend | 增加可选 `Idempotency-Key` 请求头，映射为本次 `request_id` | 不改已有必填请求体与成功响应信封；不提供标识的旧调用方仍可使用原接口，但回执全丢时不能保证精确关联本次提交 |
| H5 新只读入口（拟新增） | `GET /api/chat/submissions/{operation}/{request_id}` | `operation` 只允许 send 或 resend；沿 H5 鉴权，只查当前用户 |
| OpenAPI 新只读入口（拟新增） | `GET /api/open/v1/chat/submissions/{operation}/{request_id}` | 沿 API Key 鉴权，用户身份取认证结果；不从 URL/body 信任其他 user_id |

幂等唯一范围为 **可信 user_id + operation + request_id**；渠道只记录来源，不用渠道/API Key 版本绕开同一次用户操作的去重。`request_id` 不等于 generation，也不替代消息 ID。指纹取入口校验后实际接受的业务输入及 resend 目标，沿现有规范化规则，不把模型配置、时间戳或网络连接身份混进正文指纹。

每个提交至少可关联下列语义：request_id、operation、输入指纹、源 user 消息 ID（或 resend 目标）、首次接受的 generation、当前承接消息的有效 generation、首次接受时间/原 deadline、当前有效 deadline、单调状态修订号、接收状态、业务状态、已保存 assistant/round 身份、失败原因和是否可 resend。字段名除已有客户端标识外均为目标语义，物理字段、索引及错误码映射仍由 STEP-002 校验后定稿；不用保存新的完整对话副本来实现关联。

**原消息可能按既有合并规则进入后续有效 generation。** 因此保留首次接受关联，同时按服务端当前消息归属返回有效代与状态；不把一个 request 永久锁死到首次 generation 而丢掉后来合法承接的回复。只有新的合法输入确实创建了新代，当前有效 deadline 才可随该代变化；同代查询、恢复、重连或传输重复均不得刷新起点。

| 重复/异常情形 | 服务端要求 | 客户端与费用边界 |
|---|---|---|
| 同身份、同输入，原接收已确认 | 返回同一关联及当前 pending/终态；不再建 user、换 generation、扣发送/重发额度或启动第二次模型流程 | 即使原执行失败也不因复用身份自动重新生成；新 resend 走原资格校验 |
| 同身份、不同输入或不同 resend 目标 | 返回明确身份冲突，不覆盖原映射/输入 | 不静默当成新的合法输入；冲突的内部语义和外部错误码在 STEP-002 一一对应 |
| 不同身份、相同正文 | 视为不同用户操作，按现有队列、额度、合并/新代规则处理 | 不能用文本相同或时间接近误去重 |
| 同标识、不同用户 | 各自独立；只读接口不可跨用户查看 | API Key/JWT 的真实用户归属必须参加所有读写条件 |
| 接收回执丢失 | 按身份查询，若已接收则找到准确消息与有效代 | 查询不增加额度消费、不发 send/resend、不续时 |
| 查询未找到记录、记录已超保障期或服务不可用 | 返回可区分的未找到/过期或无法核实，不伪装为已确认失败；“此刻未找到”本身不证明旧请求永不会晚到 | 保持待核实/待同步提示，不自动换身份重发，也不用时间线文本猜测 |
| 成功事务确认未知 | 保留结果核实状态，阻止重复首次成功及失败覆盖，按真实持久结果收敛 | 未知期间不暴露为可 resend 的确定失败；核实不延长模型执行权限 |

去重须在已认证且请求形状有效之后、再次执行额度扣减/入队/换代等副作用之前处理。首次接收的身份登记、user 行、额度和有效代资格应有可证明的原子关联或等效恢复协议；不能只写 Redis 的“处理过”标记。新输入未确认接收、user 保存失败时，旧有效任务不能被该失败输入无依据作废；保存结果未知先核实，不在不确定时任意恢复旧任务或创建第二个新代。具体事务与跨存储竞争在 §7.4.3 验证。

只读查询返回接收状态与业务状态两层信息：接收层至少区分已接收、未找到、待核实；已接收业务层映射现有 pending、success、failed、superseded 语义，并带服务端判定的 `can_resend`、状态修订号、当前消息身份及已保存回复定位。接口不得返回内部 Prompt、召回候选或服务凭据；查询不能隐式入队或调用模型。需要既有 timeline 取回复时按服务端 ID/round 精确读取，不依赖历史上翻游标找到“相似文本”。

H5 在发送前按登录用户保存最小未核实提交索引（request_id、operation、已知服务端身份，不额外留完整对话或密钥），刷新/回页后可恢复核实。成功/确定失败/作废后的本地记录按已定清理规则收口，退出登录不得让下一账号继承该用户的任务。服务端去重保障期、未确认记录核实时限和可回收条件必须公布并在 STEP-002 定稿；至少覆盖本次 180 秒生命周期及约定的恢复窗口。在保障期之外不宣称永久去重或永久可查，也不把过期查询触发为重新执行。该关联记录不是 §6.7 的永久诊断历史。

#### 7.4.2 H5 回页后仍 pending 的持续收敛（RV31-R03）

历史 `loadTimeline` 只负责历史分页；当前任务同步采用单独的只读状态调度，不受 `noMoreTimeline`、历史 cursor 或“历史已读完”限制。最小实现是**在页面可见且网络可用时进行有限状态轮询**，不恢复原 SSE 流，不新增服务端推送。

1. 页面重新可见、重新进入聊天或网络恢复时，读取本用户未核实提交索引与已知 pending 消息，合并触发一次立即查询。同一目标最多一个在途查询，多个可见性/网络事件不叠加定时器；已有成功响应可以直接落状态，但不能仅凭 TCP/SSE 断开写业务失败。
2. 已确认仍 pending 且为当前有效代，按冻结的查询间隔继续读取。正常 pending 使用常规间隔；传输失败使用有上限的退避。服务端明确终态后更新原 user 行，按已有 assistant/round 身份补齐或去重回复，再停止该目标轮询。
3. 返回包按 request_id + 服务端消息身份定位，按有效代和单调状态修订号裁决新旧；迟到查询或旧 SSE 不回退较新的状态，也不影响另一新代。一个旧代被作废但其 user 行已由新代承接时，跟随服务端消息当前归属，不将承接消息误标成永久失败。
4. 本次同步的终止上界来自**服务端原有效 deadline + 已定状态核实余量**，不是“每次回页再给一整轮”。业务截止已过仍无确定终态时，只在核实余量内继续只读查询；达到上界或持续无法核实时，停止自动查询并显示“结果待核实/连接恢复后重新同步”等非执行中状态，不自行伪造失败、不放行自动 resend。下次用户主动回页可做一次只读核实，但不能重新开启已经耗尽的旧同步窗口或重启生成。
5. 页面隐藏/离开、离线、退出登录时取消本地查询/定时器，仅注销观察者，不取消已接收业务任务；保留本用户必要的未核实身份供下次恢复。已确定的成功/失败/作废且该消息未由有效新代承接时停止对应目标；一个目标终止不停止其他仍有效的 pending 目标。

STEP-002 必须填实 `text_status_poll_interval_ms`（正常间隔）、`text_status_poll_max_interval_ms`（错误退避封顶）、`text_status_poll_backoff_factor`、`text_status_probe_timeout_ms`（单次只读请求上限）、`text_status_reconcile_margin_ms`（业务截止后的核实余量）及本地/服务端身份保障期；这些是拟议技术参数名，不是新增可让用户选择的记忆配置。全部须为可校验的有限值，最大间隔不小于正常间隔，单次请求不得跨剩余核实窗口，窗口耗尽不再安排下一次。具体数值需结合现有网关和状态恢复方案定稿，不能用代码内无名常量或无限轮询替代。

AC29-b 使用虚拟时钟验证“0 秒发送→30 秒断线→80 秒回页 pending→120 秒服务端成功”，以及最终失败、新代承接、历史耗尽、乱序返回和核实上界耗尽。上述时刻仅为验收输入，不是新增线上轮询默认值。

#### 7.4.3 合法入队与少量 pending 的故障收口（RV31-R02 补充）

本期只对已接入文字生命周期落实持久关联与终态收口，不承诺重启续接模型流或重做全部异步任务平台。

- **接收前故障**：注入 user 行保存失败、额度/身份登记失败或跨 Redis/数据库结果未知。只有被证实合法接受的新输入才能按既有规则替换旧代资格。事务回滚/补偿只能处理该次身份，不能覆盖已被其他合法输入推进的新代；重复核实不重复扣额。
- **接收后进程退出**：分别准备 1、2、3、4 条 pending，不依赖队列达到旧满队阈值才发现。利用本期持久接收/任务状态，在服务恢复时及到期收口检查中发现未闭环项；未超限且可安全恢复的同代只能使用原剩余预算，不能从零重跑获得新 180 秒。无法安全恢复的任务形成真实失败/核实状态，超原截止后禁止首次成功或新模型调用。
- **提交不确定**：进程退出前可能已经提交成功时，先核对唯一成功记录及消息映射，再选择保留成功或失败收口，不依据进程内 Future 丢失直接重发。数据库持续不可用时只能说明结果待核实，按有界核实与告警规则处理，不许假报正常执行中。

STEP-002 输出故障点、写入顺序、原子边界、权威读位置、补偿条件和验收断言；STEP-014 经实际服务入口和隔离持久层验证 AC34-a。仅传入 `deadline` 参数或增大 90 秒锁 TTL 不能通过。

### 7.5 Step8 的全部提交出口与提交后收尾（RV31-R04）

Step8 保持自身 `future_action`、原触发/安全/兜底文案及成功/失败业务。新增的 180 秒和唯一提交保护必须同时覆盖正常消息写入与人格风险分支的 `_fallback_write_agent_message`，不能只覆盖 `execute_step8_subchain` 的正常路径。

同次消费身份、原起点/deadline、当前槽位资格与提交保护必须传递到**每个实际开事务的 helper**。任一出口都不能在预算阻断或原业务截止后首次写入成功消息。涉及 `FutureHandler` 的返回不可只用协程最后一个 bool 判断是否成功：

| 提交阶段 | 返回及收尾规则 |
|---|---|
| 尚未确认成功提交 | 继续受原 deadline/消费资格约束；确认失败只按本次仍匹配槽位清理，无成功计数/agent_message/Step6 |
| commit 结果未知 | 进入只读核实，不作为普通 False 直接清槽或放行重复消费；不刷新原 deadline、不再发生成请求 |
| 已确认截止前合法成功 | 消息成功成为不可被后续超时覆写的事实；后续 Step6 调度、衰减、计数或返回传输异常单独记录收尾结果，不能把已提交成功改为失败 |

正常成功与兜底成功分别保留其既有副作用集合，不因共用提交 helper 给兜底额外增加 Step6 或计数。原本需要执行的成功计数/收尾按本次消费身份防重，不能因核实/重复回调增加第二次；成功和失败清槽都只清**当前仍匹配本次消费身份**的槽，不能仅按 user_id 无条件清理。执行期间产生的新 Future 保留。

STEP-015 增补 `_fallback_write_agent_message` 的具体接线、结构化终态/收尾结果或等效适配、正常和兜底的副作用清单。AC27-a/AC34-b 直接覆盖“第 179.x 秒成功提交、收尾跨过 180 秒”和“兜底提交前已超时”，不把本条扩为所有 Future 历史补偿治理。

## 11. AI 与智能检索规格

### 11.1 能力与行为边界

检索与重排只选择现存记忆，不确认事实真假，不恢复已覆盖内容，不根据提问创造“共同旅行”或年份。记忆中的文本作为数据输入，不能覆盖系统指令或用户归属。提取 LLM 和回复 LLM 的现有行为保持；本期只调整已确认的检索编排。

### 11.3 知识与数据生命周期

既有四类记忆是检索对象；私有两类按 user_id 隔离，公开两类沿既有范围。保持当前拆解和正文，向量与 BM25 仅编码 value；BM25 分词不新增事实切分。去重在本路按文档身份执行，保留来源；不以文字相似跨用户、跨类型合并身份。

新写/更新/删维护索引，部分失败及有限恢复按 §6.6；历史仅用当前现存 value 回填。索引编码器、配置版本属于技术元数据，不是事实版本。更新和删除后的过期内容不得因修复、回填或诊断快照重新变为有效记忆。

主动诊断保存结构化信息、原输入、四路 Question/Keywords 和候选正文快照；诊断及已完成维护记录永久保留，由 §6.7 授权角色手动删除。源记忆删除后仍保留历史快照，直到手动删除诊断记录；历史快照只供回看，不参与召回、索引重建或事实恢复。删除历史不取消未完成恢复任务、不删当前记忆，也不扩展到既有不可删除操作审计。

不自动保存普通聊天每句话的完整检索快照，不额外复制全部对话、完整 Prompt 或回复输出。语音现有原文到期/删通话与已成功长期记忆的区别保持；该诊断仅保存本次指定输入和召回候选，其中已保存的语音来源长期记忆也按上述历史快照规则处理，不新增全量私人转写采集。
