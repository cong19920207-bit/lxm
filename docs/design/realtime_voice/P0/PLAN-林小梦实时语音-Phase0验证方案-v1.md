# 林小梦实时语音 Phase 0 验证方案

> 版本：v1.1  
> 日期：2026-07-26  
> 状态：已确认，待拆解实施  
> 上游需求：[`PRD-林小梦实时语音通话-正式版-v1.md`](PRD-林小梦实时语音通话-正式版-v1.md)  
> 定位：本文档只规定 Phase 0 可行性验证，不替代正式 PRD，不授权开发 Phase 1 业务功能。

---

## 1. 结论与核心决策

Phase 0 采用“**会前预加载 + 规则触发 + 单次 Embedding + 用户记忆单路检索 + 超时降级**”方案。

当前文字对话的 Step1.5 LLM 查询改写和 Step2 四路检索不进入实时语音关键链路。原因是 Step1.5 存在额外 LLM 调用，延迟上界与实时语音约 1 秒的记忆召回预算不匹配。

Phase 0 不复制、不修改现有 Step1.5/Step2，也不调用或改造现有 `embedding_service`、`dashvector_client`。为避免现有文字链路的时延、超时和缓存策略进入实验链路，Phase 0 在独立命名空间内复刻所需的底层只读调用：单次 Embedding、DashVector `user` 路检索，以及人格、关系、最近文字对话读取。

复刻以现有实现的请求协议和数据格式为参考，但 Phase 0 独立维护 1 秒检索总预算、超时取消、迟到结果丢弃和实验事件记录。它不反向影响原有业务，也不承诺在 Phase 1 直接迁移；验证结束后按结论选择删除、重写或重新设计。

### 1.1 为什么多路 RAG 不一定很慢

市面上的多路或混合召回通常不会串行调用多个 LLM，而是采用以下方式：

1. 只在需要外部知识时触发检索，不每轮检索。
2. 查询只生成一次 Embedding，多索引或多策略并行执行。
3. 使用 ANN 向量索引、小 `top_k`、元数据过滤缩小搜索空间。
4. 使用 RRF 或简单权重合并已排序结果，不再额外调用大 LLM 重排。
5. 把高频上下文会前预加载或在后台预取，实时回复优先命中缓存。
6. 为慢路设定硬超时，未命中时诚实降级，不阻塞语音回复。

Azure AI Search 的公开文档明确描述了全文与向量查询并行执行、再用 RRF 合并的方式；Google Cloud Vector Search 也提供稀疏/稠密向量在同一索引中运行并用 RRF 融合的混合检索。这说明“多路”本身不是主要延迟来源，**串行 LLM 改写、LLM 重排、跨地域网络与过大注入上下文**才更容易拉长关键路径。

语音场景比文字场景更严格。2026 年的 VoiceAgentRAG 研究采用后台慢思考器预取记忆、前台快速说话器优先读语义缓存的双路架构。Phase 0 不需要一次实现该完整架构，但采用的“会前小包 + 按需快速召回”与其低延迟思路一致。

## 2. Phase 0 目标

Phase 0 的目的不是实现可上线的语音通话产品，而是在不影响现有文字业务和生产数据的前提下，验证豆包 S2S 是否具备进入 Phase 1 正式架构设计的最低可行性。输出应是可复核的 Go / Conditional Go / No-Go 证据，而不是一次演示成功或可直接上线的代码。

Phase 0 只回答以下三个 Go/No-Go 问题：

1. 豆包 S2S-Strong Character 的音色、情感表达和人格一致性是否达到“是同一个林小梦”的标准。
2. 用户打断、首帧延迟、弱网与长通话稳定性是否达到实时语音体验底线。
3. 会前小包与会中用户记忆单路检索能否在时延预算内完成，并被豆包自然使用。

---

## 3. 非目标

Phase 0 不实现：

- 正式 H5 通话页面与首页/聊天页入口。
- 微信 JSSDK 、微信内置浏览器和 iOS 微信兼容性。
- 语音余额、计费、充值与关系成长。
- 正式 `voice_call` / `voice_memory_candidate` / `voice_pending_topic` 表。
- 会后记忆炼制与 DashVector 写入。
- 危机内容检测与后台管理。
- Step1.5 LLM 查询改写、Step2 四路召回、LLM reranker。
- 正式生产部署、真实用户灰度或付费实验。

Phase 0 通过不代表微信 H5 链路已可行；该能力须在后续独立验证。

Phase 0 不把实验实现视为生产实现：测试页面、S2S 状态机、实验客户端、事件格式和导出逻辑均可在结论形成后删除；只有经后续设计评审确认的需求，才重新设计并进入 Phase 1。

## 4. 隔离架构

```text
Phase 0 测试页面（Chrome Desktop）
    │ 麦克风音频 / 播放音频 / 测试控制
    ▼
Phase 0 独立实时语音测试服务
    ├── 豆包 S2S-SC 连接与鉴权
    ├── 音频流上下行与打断
    ├── 会前小包组装器
    ├── 语音记忆实验链路
    │     ├── 规则触发
    │     ├── 确定性查询构造
    │     ├── 独立 Embedding HTTP 客户端（单次）
    │     └── 独立 DashVector HTTP 客户端（user 路 Top3）
    └── 事件时间线与测试报告导出

Phase 0 本地只读查询实现
    ├── 实际生效人格配置读取
    ├── relationship / 关系与称呼读取
    └── conversation_log / 最近文字对话读取
```

测试服务、实验客户端和本地只读查询实现必须保持独立命名空间，不挂载到正式用户入口，不导入现有文字链路的服务对象，不改变现有文字对话链路。

复刻边界如下：

- 可以参考并复制现有底层请求协议、字段格式和只读查询语义；复制后的代码只供 Phase 0 调用。
- 不复制 Step1.5、Step2、Step6 或文字聊天编排；这些流程既不进入实时关键路径，也不因 Phase 0 改动。
- Phase 0 独立客户端不使用现有 Embedding 的 Redis 缓存读写，避免测试转写或向量结果进入共享缓存。
- Phase 1 如需同类能力，须重新评审正式接口、超时、缓存、可观测性和数据治理；不得将 Phase 0 代码直接挂入生产入口。

## 5. 会前小包

### 5.1 数据范围

Phase 0 小包只包含已有数据：

| 内容 | 来源 | Phase 0 处理 |
| --- | --- | --- |
| 人格核心 | 当前实际生效的人格配置 | 测试开始时导出固定快照并记录 SHA-256，整轮测试不热更新 |
| 关系阶段与称呼 | `relationship` | 只读 |
| 最近文字对话 | `conversation_log` | 只读后确定性截断，不调用 LLM 压缩 |
| 高价值用户记忆 | DashVector `type=user` | 在本地测试配置显式列出最多 5 个 `doc_id`，读取后再校验 `user_id` 归属 |
| 上次通话摘要 | 尚无数据源 | 固定为空 |
| 待续话题 | 尚无数据源 | 固定为空 |

### 5.2 时间预算

- 完整小包 P95 不超过 3 秒。
- 3 秒内未完成时，降级为“人格核心 + 关系阶段与称呼”。
- 每个数据源单独记录延迟，不只记总耗时。

## 6. 会中记忆召回

### 6.1 触发原则

每轮 ASR 最终转写文本先经过轻量规则，非触发轮次不生成 Embedding、不访问 DashVector。

Phase 0 触发词使用本地测试配置，初始集合为：

- 上次
- 你还记得
- 我之前说过
- 我之前告诉过你
- 那个朋友
- 继续说
- 我们之前

Phase 0 不引入 NER 组件。固定触发集合的目的是验证延迟与外部记忆注入，不是完成正式的召回覆盖率。

### 6.2 查询构造

不使用 LLM 改写。查询由确定性规则构造：

1. 当前 ASR 最终转写作为主文本。
2. 当当前文本存在“这个/那个/他/她/之前的事”等弱指代时，前置拼接最近 2 轮用户与角色转写。
3. 过滤空文本、纯语气词与超出测试上限的内容。
4. 对构造后的完整查询执行 Unicode NFKC 归一化、合并连续空白、去除首尾标点，再以 SHA-256 作为通话内缓存 key。

### 6.3 检索

```text
ASR 最终转写
  → phase0_should_recall
  → phase0_build_query
  → phase0_embedding_client.get_embedding（一次）
  → phase0_dashvector_client.search
       memory_type=user
       user_id=当前测试用户
       top_k=3
       threshold=0.7
  → format_rag_context
  → 豆包外部 RAG 注入
```

语音召回实验链路只使用独立复刻的 Phase 0 客户端，不调用 `embedding_service`、`dashvector_client.search`、`execute_query_rewrite` 或 `execute_multi_vector_retrieval`。其 HTTP 请求协议与数据过滤规则可参考现有实现，但超时、缓存和事件记录独立管理。

### 6.4 时间预算与降级

| 阶段 | 目标 |
| --- | ---: |
| 触发规则 + 查询构造 | P95 ≤ 20ms |
| Embedding | 单独记录，不预先假设供应商延迟 |
| DashVector 检索 | 单独记录，不预先假设供应商延迟 |
| 检索总耗时 | P95 ≤ 1 秒 |
| 注入后到首帧音频 | P95 ≤ 3 秒 |

处理规则：

- 1 秒内完成：正常注入记忆。
- 超过 1 秒：放弃当次检索，不让过期结果污染后续轮次。
- 检索无结果：不注入空的共同经历，由语音 Prompt 要求角色诚实表达暂时想不起来。
- 通话内相同规范化查询：复用内存缓存，通话结束即释放。

## 7. 测试页面与安全边界

Phase 0 页面只服务于内部测试，仅要求 Chrome Desktop。页面包含：

- 测试用户 ID 选择。
- 候选音色和人格版本选择。
- 开始/结束会话、静音、清空通话内缓存。
- 实时状态：连接、在听、检索中、在说、降级。
- 事件时间线：ASR 完成、触发、Embedding 完成、检索完成、RAG 注入、首帧音频、打断、停播。
- 当轮召回结果和丢弃原因。
- JSON/CSV 报告导出。

安全边界：

- 所有豆包、Embedding 和 DashVector 凭据只存在服务端，不下发到浏览器。
- 默认不保存原始音频。
- 不向 MySQL、Redis、共享 DashVector 写入测试结果、测试配置或测试向量；独立 Embedding 客户端不使用共享 Redis 缓存。
- 测试日志不记录凭据，转写仅保存在当次本地测试报告中。
- 测试用户必须位于显式白名单；测试用户与真实用户隔离，不读取未授权的真实用户记忆。

## 9. Go / Conditional Go / No-Go

### Go

人格、实时交互和记忆三类硬指标全部达标，可进入 Phase 1 正式架构设计。

### Conditional Go

人格和通话交互达标，记忆召回 P95 在 1～3 秒之间，但超时降级稳定、不阻塞通话。可进入 Phase 1，但须把预取/缓存作为前置优化项。

### No-Go

出现任一情况则不进入完整开发：

- 人格一致性或情感表达明显不达标。
- 无法稳定打断，或首帧延迟达不到通话体感底线。
- 豆包无法接受外部 RAG 结果并自然播报。
- 长通话频繁断开、音频乱序或资源无法释放。
- 记忆未命中时高频编造共同经历。

## 10. 开发边界

后续实施步骤必须保持以下边界：

1. 新增代码全部位于 Phase 0 测试命名空间，不修改 Step1.5、Step2、Step6、`embedding_service`、`dashvector_client` 和现有文字聊天业务逻辑。
2. Phase 0 以独立复刻为原则：底层 HTTP 调用和只读查询实现复制到实验命名空间，不将测试时延、超时、缓存或日志策略抽取为共享能力。
3. 不新增生产数据表、不写入 MySQL、Redis、共享 DashVector，不发布后台配置。
4. 任何需要修改现有共享服务、复用现有服务对象或将实验路由接入正式入口的要求，均必须退回设计评审，不以 Phase 0 方便之名直接改动。
5. Phase 0 结论形成后，逐项标记实验内容为“删除”“仅保留证据”或“Phase 1 重新设计”；不得默认迁移实验代码。
6. Phase 0 报告必须同时保留成功与失败样本，不用单次演示成功代替统计结论。

## 11. 后续顺序

1. 将本方案拆成独立可验收的 Phase 0 开发步骤。
2. 先跑通豆包 S2S-SC 裸通话，再接入会前小包。
3. 在裸通话稳定后接入单路用户记忆召回。
4. 按固定测试矩阵收集数据，不边测边改通过线。
5. 输出 Go / Conditional Go / No-Go 报告，再决定是否进入 Phase 1。
