# 零、全局说明与依赖

## 0.1 功能定位
类似"微信语音通话"心智——App 内实时双向语音，不涉及电话网/SIP。

## 0.2 核心设计原则
- **独立业务线**：语音通话、语音记忆、通话内容安全均为新增独立模块，不修改 Step6、AGE003、现有 Doubao 文字对话链路的既有代码路径；如与现有模块有相同数据诉求，可借鉴其设计范式或复刻其逻辑，但不共用同一处理节点。
- **不改动现有稳定系统**：`lxm_base_persona`、四路 DashVector 检索基建、`banned_keywords` 配置模式等予以复用（读取/借鉴范式），但不侵入其代码路径。
- **Anti-AI authenticity 一致性**：语音场景下的诚实与拟人原则与文字对话保持一致（角色永不承认AI身份，但检索失败时诚实告知、不编造记忆）。
- **技术限制用角色化语言包装**：余额耗尽、接通失败等系统层面的限制，统一用"角色原因"包装（信号不好/不方便接电话），不暴露系统措辞。

## 0.3 模型选型结论
- **Phase 0 仅测试豆包端到端实时语音大模型**（火山引擎），通过即直接锁定，不设 OpenAI/Qwen/Gemini 并行候选。
- **不做级联备用方案**（不采用 ASR+LLM+TTS 拼接方案作为兜底）；豆包裸测未通过时接受延期或维持现状。
- **首发地域仅限中国大陆**，不考虑跨境网络与合规问题。

## 0.4 Phase 0 前置验证项（本文档部分参数依赖以下验证结果，验证前均为预估值）
1. 豆包端到端语音的拟人度/情感表达是否满足"是不是同一个林小梦"的核心标准（真人盲测）
2. 豆包端到端语音是否支持 function calling / 工具调用（决定 3.3 节"会中检索增强机制"能否落地）
3. 现有四路 DashVector 检索在语音场景下的实际延迟（决定 3.3 节检索超时参数的最终取值）

# 一、方案概述

## 1.1 整体架构
```
用户发起通话
    ↓
VOICE001 通话核心（发起/接通/通话中/挂断）
    ↓ 通话中按需调用 ←──────────┐
VOICE002 语音记忆                │
  ├─ 会前小包（一次性预加载）      │
  ├─ 会中按需检索（复用现有四路检索基建，见3.3）
  └─ 会后记忆炼制（借鉴Step6范式，独立表/独立流程）
    ↓
写入共享 DashVector 四路索引（打 source=voice_call 标记）

通话全程并行 ←─────────────────┘
VOICE003 通话内容安全（危机检测/资源展示/隐私过滤）
```

## 1.2 与现有系统的关系

| 现有系统 | 语音通话如何对待 |
|---|---|
| `lxm_base_persona` | 复用其核心人设文本，语音人格卡在此基础上精简（见第五章） |
| Step6 记忆抽取 | 不复用代码路径，VOICE002 借鉴其 11 字段抽取范式独立实现 |
| 四路 DashVector 检索 | 直接复用（同一套索引、同一套 `top_k`/`threshold` 配置），读取层面共享 |
| AGE003 / Future 槽 | 不接触。VOICE002 的"待续话题"字段独立维护，不写入现有 Future 槽（详见 3.4） |
| `banned_keywords` Redis 配置模式 | 借鉴其"可配置列表"模式，语音危机关键词/召回触发词各自开独立 key，不混用 |

# 二、VOICE001 通话核心

## 2.1 核心职责
承接通话发起、接通、通话中状态管理（计费/静音/网络异常）、挂断的全流程，并在关键节点触发 VOICE002/VOICE003。

## 2.2 通话入口
- **主入口**：首页"语音通话"按钮（现有 `frontend/pages/index.html` 中 toast 占位改为真实入口）
- **次入口**：聊天页右上角新增电话图标
- **动态入口**：Phase 2 再做，不在本版本范围（原调研报告第17节将此列为 MVP，已作废，见第十一章）

## 2.3 通话发起流程

```
用户点击入口
  → 首次使用：展示简短说明"会生成转写与摘要，默认不保存原始音频"
  → 校验麦克风权限
      ├─ 拒绝：仅阻断本次发起，文字聊天等其余功能不受影响
      └─ 通过：继续
  → 校验剩余余额
      ├─ 余额 = 0：toast"对方当前不方便接电话，可以打字留言哦"，不建立会话
      └─ 余额 > 0：建立语音会话，同时触发 VOICE002 会前小包准备（见3.2）
  → 8 秒内未成功接通：toast"可能手机没有在手边，要不等会再试试？"，不建立会话
  → 接通成功：由林小梦先开口
```

**H5 多场景接入**：用户经由微信内置浏览器和独立浏览器访问均需支持。微信内置浏览器场景下标准 Web `getUserMedia` 存在兼容性问题（尤其 iOS），需额外接入微信 JSSDK 录音接口（需提前绑定安全域名、完成公众号权限配置）；独立浏览器场景走标准 Web API 即可。两套方案需同时具备，不能只做一套。

## 2.4 通话中

### 2.4.1 开场与轮次
接通后由林小梦先开口（当前场景均为用户主动发起通话）。

### 2.4.2 实时语音交互规则
> ⚠️ **待确认**：以下为调研报告原方案，尚未经过逐项确认，你提出会自行复核后给出细节意见。**其中"长沉默"一档与本节 2.4.3 的静音强制挂断规则存在数值冲突，需在复核时一并解决**（见冲突说明）。

| 项目 | 原方案（待确认） |
|---|---|
| 谁先说 | 接通后 0.4–0.8 秒由林小梦先说，开场 ≤ 6 秒；10 分钟内重拨时改为"刚刚断啦，我还在" |
| 断句 | 优先语义 VAD；短"嗯/啊/对"且无新语义视作附和，不自动打断 |
| 打断 | 用户持续发声约 180–250ms 即停止播放；服务端标记已播放到的位置，未播放内容不写入"用户听到的记录" |
| 普通停顿 | 0–2.2 秒不抢话；4–6 秒可轻声"嗯，我在听"；12–20 秒按情境只追问一次 |
| 情绪停顿 | 允许 8–12 秒安静；不连续问"怎么了"；用户明确要安静时不主动填充 |
| 长沉默 | 60–90 秒询问是否继续陪着；3 分钟无有效语音自动结束 ⚠️**与下方 2.4.3 冲突** |
| 回复长度 | 日常首答 3–8 秒；情绪承接 2–6 秒；复杂建议分段，每段 ≤ 12 秒并让出话权 |
| 口语风格 | 短句、自然自我修正、少量"嗯/诶/哈哈"；笑、叹气只在语义匹配时出现，不做每句装饰 |
| 失败兜底 | 低置信 ASR 时复述确认；两次听不清后建议转文字；模型超时先发 0.5–1 秒自然承接音，不编造答案 |

**⚠️ 数值冲突说明**：C8（已确认）规定"双方连续10秒无有效语音，服务端强制结束通话"，定位是**网络异常/App崩溃兜底**，不是情绪停顿处理。但上表"长沉默"档给的是 60-90秒才询问、3分钟才结束，是**正常对话中的情绪停顿处理**。两条规则字面上矛盾——如果 C8 按 10 秒字面执行，用户一次正常的情绪沉默（比如安静哭一会儿）就会在真正进入"长沉默"处理逻辑前被强制挂断，整套分层沉默处理形同虚设。复核本节时需要明确：**10 秒规则的"无有效语音"判定，应理解为麦克风完全无声音信号输入（更接近网络/设备异常的信号特征），而非"用户安静但通话连接正常"**——即需要用某种信号（比如是否仍检测到环境音/呼吸音等基础音频活动）区分"真的断了"和"用户在安静"，而不是两套阈值直接打架。这个判定逻辑的具体实现方式，建议在你复核本表时一并定案。

### 2.4.3 静音与网络异常兜底
- **静音强制挂断**（C8）：双方连续 10 秒无有效语音（信号层面判定，见上方冲突说明），服务端强制结束通话——用途是防止网络异常/App后台崩溃导致通话空转消耗余额，非情绪停顿处理机制
- **网络异常重连**（C22）：与静音判定分开处理，网络异常先进入重连宽限窗口，宽限期内恢复则继续通话，超时未恢复才计为通话结束

### 2.4.4 余额与计费
- 余额制（按秒计），新用户默认 600 秒，后台可查询/可手动充值，暂不做每日重置等额外限制
- 余额扣减至 0：不提前预警，通话即时停止，停留在通话页面，5秒倒计时，toast"对方信号不好，可以文字继续哦～"

### 2.4.5 危机检测（触发点，详细设计见 VOICE003）
每轮 ASR 转写文本经过 VOICE003 危机检测，命中则并行触发独立存储与资源展示，不中断本节流程。

## 2.5 挂断与结束
通话结束（正常挂断/静音超时/网络异常超时/余额耗尽）→ 触发 VOICE002 会后记忆炼制（见3.4）。用户侧不展示通话摘要卡片，不提供本次通话删除入口（见第八章边界情况）。

## 2.6 数据结构
```
voice_call:
  call_id
  user_id
  start_time
  end_time
  duration_seconds
  end_reason        # 正常挂断 / 静音超时 / 网络异常超时 / 余额耗尽
  entry_point        # 主入口 / 次入口（为 Phase 2 动态入口预留字段）

user_voice_balance:
  user_id
  remaining_seconds
  last_updated_by     # 后台操作人，充值记录
```

## 2.7 后台管理
见第九章统一规划。

## 2.8 模型选型
豆包端到端实时语音大模型（火山引擎），Phase 0 裸测验证拟人度是否达标，见 0.4。

# 三、VOICE002 语音记忆

## 3.1 核心职责
独立于 Step6 的语音记忆全生命周期管理：会前加载、会中按需检索、会后炼制写入。与 Step6 借鉴同一套抽取范式（11字段 JSON、`stable_key` upsert 约定），但代码路径、数据表完全独立。

## 3.2 会前记忆加载（"小包"）

### 3.2.1 触发时机
用户点击"发起通话"的瞬间开始后台准备，与 2.3 节的 8 秒接通判定共用同一等待窗口；接通那一刻小包必须已就绪。

### 3.2.2 内容与取数逻辑

| 内容 | 取数方式 | 字数上限 |
|---|---|---|
| 人设核心 + 关系阶段 | 直接读取 `lxm_base_persona` + 当前关系等级 | 不限（固定文本） |
| 最近对话压缩摘要 | 文字消息记录 + 语音通话记录按时间戳合并，取最近轮次一起压缩（不分来源） | ≤500字 |
| 上一次通话摘要 | 查最近一条 `voice_call` 摘要；用户从未打过电话则为空，不报错 | ≤250字 |
| 最近30天高价值记忆 | 复用现有 DashVector"用户记忆"索引，按时间+重要性取 Top5 | 每条≤150字，共≤750字 |
| 待续话题 | 语音记忆服务独立维护的"待续话题"字段（见3.4.3），**不写入现有 Future 槽，不与 AGE003 产生接触** | ≤100字，1条 |
| 动态相关 | Phase 2 才启用的字段，本版本恒为空 | — |

**小包总量**：约 1600-1800 字（不含人设核心本身）。

### 3.2.3 准备超时兜底
小包在 **3 秒**内未准备完成，直接降级为"仅人设核心+关系阶段"的最小可用版本接通，不因等待小包而拖慢接通速度。

## 3.3 会中按需检索

### 3.3.1 触发机制（两层设计）

**主机制（不依赖模型能力，现在就能实现）**：每轮 ASR 转写完成后做同步的关键词/实体匹配：
- 固定短语（"上次/你还记得/那个朋友/继续说/我之前告诉过你"）：复用 `banned_keywords` 式 Redis 可配置列表模式，新开 `memory_recall_trigger_keywords` key
- 具体人名/地点：需要**命名实体识别（NER）**能力，这是独立的技术依赖点，不是"配置几个词"能覆盖的，需单独技术组件支持

**增强机制（依赖 Phase 0 验证结果，设计先行）**：若豆包端到端语音支持 function calling/工具调用，可升级为模型自主判断"当前是否需要检索"并主动调用检索工具。**开发阶段若验证豆包不支持此能力，此层直接跳过（pass），不影响主机制运行**。

非触发轮次完全不检索，避免每轮都查带来的额外延迟和调用开销。

### 3.3.2 检索流程与参数

1. 命中触发 → 异步调用现有 `multi_vector_retrieval_service.py`，沿用同样的 `top_k=3`、`threshold=0.7`，不新开语音专属阈值
2. 检索耗时 **<800ms-1秒（预估值，待联调实测校准）**：直接自然带入回复，不使用过渡话术
3. 检索耗时超过软超时：使用过渡话术"你说的是之前提过的那件事吗，我想一下"（此话术需写入语音人格 Prompt，非模型自带能力，见第五章）
4. 检索耗时超过硬超时 **约3秒（预估值，待联调实测校准）**：放弃本次检索，诚实回应"这个我一下想不起来"，不编造共同经历
5. **缓存去重**：同一主题 10 分钟内命中过直接用缓存结果，内存级缓存，通话结束即释放，不落库

> ⚠️ 以上延迟参数均为估算值，非实测数据，需在 Phase 0 豆包接入 + 现有四路检索联调后用真实延迟数据重新标定。

## 3.4 会后记忆炼制

### 3.4.1 触发与范式
通话结束 → 转写文本（仅"用户实际说的"+"AI实际播放出来的"，被打断未播放部分不计入）进入独立语音记忆炼制服务 → 借鉴 Step6 的 11 字段 JSON 抽取范式，独立 prompt、独立 LLM 调用。

### 3.4.2 敏感度两档处理
- **一档（合并原一/二档）**：一般信息 + 姓名/日期/金额/地址/健康/性取向/宗教/亲密关系/工作单位/ASR低置信内容 —— 自动写入 + 后台开关控制是否参与召回，默认开
- **二档（原三档，范围已收窄）**：第三方隐私类信息，明确限定为**支付密码、身份证件、支付信息、原始声音**（后台可扩展类型）—— 抽取 prompt 层面直接指示跳过，不生成不写入，不走"存了再控制召回"路径

### 3.4.3 待续话题（独立字段，方案A）
语音记忆服务自行提炼"下次可以接着聊的事"，作为独立字段供下次通话的会前小包读取。**写法上可借鉴现有 Future 槽的提炼思路，但物理上是完全独立的数据表和触发路径**，不写入 Future 槽，不触发 AGE003 的主动消息调度，两者互不接触。

### 3.4.4 写入
写入共享 DashVector 四路索引，`stable_key` 打 `source=voice_call` 标记（不影响召回，仅用于后续按来源审计/批量处理）。

## 3.5 Prompt 模板示例
> 具体模板内容留待开发阶段与 Step6 现有 prompt 结构对照细化，此处标注需包含的字段清单：11 个基础字段（同 Step6）+ `source_call_id` + `asr_confidence` + `sensitivity_tier`（一/二档）。第三方隐私类字段（支付密码/身份证件/支付信息/原始声音）在字段说明中直接注明"遇到以上内容，本字段输出'无'"。

## 3.6 数据结构
```
voice_memory_candidate:
  （借鉴 memory_llm_service.py 现有 11 字段结构）
  + source_call_id
  + asr_confidence
  + sensitivity_tier      # 一档 / 二档
  + recall_enabled        # 后台开关，一档默认 true

voice_pending_topic:      # 待续话题，独立表，不接触 Future 槽
  user_id
  topic_text              # ≤100字
  created_at
  consumed_at              # 被下次通话小包读取后标记消费时间
```

## 3.7 后台管理
见第九章统一规划。

# 四、VOICE003 通话内容安全

## 4.1 核心职责
危机内容检测、独立存储、用户侧资源展示；第三方隐私类内容的抽取阶段拦截（与 VOICE002 3.4.2 二档处理为同一套配置，此处仅描述检测/响应逻辑）。

## 4.2 危机检测

### 4.2.1 覆盖范围（明确的已知限制）
**当前版本仅覆盖自伤/自杀倾向**。调研报告原提及的未成年人性内容、性暴力、跟踪控制、医疗危机、诈骗等其他风险类别，**明确列为已知未覆盖**，不在本版本处理范围内。

### 4.2.2 检测方式
纯关键词匹配（`crisis_keywords`，Redis 可配置列表，复用 `banned_keywords` 模式），不叠加语义/LLM判断层。接受"隐晦表达可能漏检"为已知限制。误判代价不对称：漏检代价高、误判代价低，因此选择宁可宽松触发的策略。

### 4.2.3 独立存储
命中后，逐字原文独立储存，**脱离记忆系统**，不参与召回、不被角色感知。这不是"记忆分档"问题，而是这类内容本身不该被当作"陪伴素材"对待——被角色不合时宜地提起，是二次伤害而非陪伴感。

## 4.3 危机资源展示

**展示形式**：语音通话界面内嵌的非阻断式提示卡片，视觉样式与聊天气泡/角色语气明确区分（系统级样式，非角色语气），让用户清楚这是"平台"提示，不是"林小梦"在说话。

**展示内容**："如果你正在经历困难，这里随时有人可以聊聊：全国心理援助热线 12356（24小时，免费）[一键拨打]"——使用全国统一号码，不展示地区分线或个人电话。

**时机与频率**：本通话内首次命中即展示一次，保留常驻小入口可重新查看，不重复弹出。

**不中断通话**：不因触发而挂断/限制对话——此时最需要陪伴延续，粗暴挂断可能造成被抛弃感，与安全提示初衷相悖。

**范围**：当前仅语音通话场景生效，文字对话场景后续迭代跟进（不在本版本范围）。

## 4.4 第三方隐私类内容处理
见 3.4.2，抽取阶段直接跳过，不生成不写入。类型可在后台扩展（`sensitive_field_types` 配置）。

## 4.5 已知限制汇总

| 限制项 | 说明 |
|---|---|
| 危机检测覆盖范围 | 仅自伤/自杀，其余风险类别不处理 |
| 危机检测方式 | 纯关键词，隐晦/间接表达可能漏检 |
| 语音安全 vs 文字安全 | 危机资源展示当前仅语音场景有，文字对话侧同类能力尚未建设 |

## 4.6 后台管理
见第九章统一规划。

# 五、语音人格与边界 Prompt

## 5.1 与现有人设的关系
语音人格卡在 `lxm_base_persona` 基础上精简，只注入对声音和行为有用的信息（基础人设、说话风格、当前关系阶段与称呼、可引用的近期生活事件）。

**⚠️ 技术债前置依赖**：人设口径存在三版本不一致（代码兜底2149年未来研究员版 / 5月测试实录24岁模特版 / PRD v1.9参考文案26岁版），语音人格卡文案**不能提前写死**，需等独立核实线上 `admin_config` 实际生效内容后再定稿。此项与语音开发解耦，可并行推进，不阻塞排期。

## 5.2 AI 身份边界（C19，项目级铁律）
角色永远不承认自己是AI/程序/语言模型，即使被直接询问身份也保持角色。**不采用**调研报告原建议的"我是林小梦，你的AI伙伴/虚拟伙伴"这类软化表述。语音场景与文字场景要求一致。

## 5.3 情感边界规则（C25）
不把"粘人"表现为控制、嫉妒、阻止现实交往，或因用户离开而施压。在 5.2（永不承认AI）确定的前提下，这条边界规则的重要性进一步提升——正因角色会一直坚持自己是真人，更需要这条硬约束防止"粘人"人设滑向真实的情感操控。

## 5.4 语音专属表达规则
- 禁止直接朗读 emoji、颜文字、Markdown 或多气泡格式
- 书面多段回复改为口语"一个点—停顿—让用户接话"
- 人设中的职业/审美背景体现在谈吐与生活细节中，不应每通电话都自报身份
- 同一人物可随情境改变语速和情绪，但基准音色、口头习惯和价值边界保持稳定

## 5.5 过渡话术
检索等待期的自然桥接话术（见 3.3.2），需写入本 Prompt，非模型自带能力。

## 5.6 后台可配置性
以上全部内容需支持后台编辑，不写死在代码里。见第九章。

# 六、关系成长机制

- **机制**（C11）：有效通话日 + 里程碑触发，不做逐分钟计分（防止诱导刷时长）
- **具体分值**（C26）：首通 +5，每个有效通话日 +5，单日有效语音 ≥10分钟额外 +10，每日语音成长上限 20
- 客户端不提供关系成长相关开关，为纯服务端逻辑，仅后台可见记录

# 七、页面与交互结构

## 7.1 通话前
- 角色头像、名称与关系称呼
- "语音通话"主按钮；首次展示简短说明："会转成文字与摘要，默认不保存原始音"
- 麦克风权限提示；余额提示

## 7.2 通话中
- 大头像/轻微呼吸动效，不做假视频
- 顶部：角色名、连接状态、通话时长
- 中部：明确的"在听 / 想一下 / 在说"状态提示
- 底部：静音、扬声器、结束（**不含字幕**，C12 已确认字幕功能 MVP 阶段不做，非原调研报告"字幕默认关闭"的降级处理，而是整个功能不存在）
- 网络异常：非阻断提示 + 自动重连（见 2.4.3）
- 不展示 token、波形技术指标、长转写瀑布或"AI 正在生成"等技术痕迹

## 7.3 通话后
**用户侧**：无摘要卡片展示，无"她想记住的事"确认/编辑/删除界面，无本次通话删除入口（C10/C14 已确认，原调研报告此处的完整交互设计已作废，见第十一章）。用户仅可"继续打字"或"再打一次"。

**管理后台侧**：通话摘要、记忆候选完整可见，见第九章。

# 八、边界情况汇总

| 场景 | 处理方式 |
|---|---|
| 8秒未接通 | toast"可能手机没有在手边，要不等会再试试？"，不建立会话 |
| 麦克风权限被拒绝 | 仅阻断本次语音发起，文字聊天等其余功能不受影响 |
| 余额为 0 时尝试发起通话 | 拦截，不建立会话，toast"对方当前不方便接电话，可以打字留言哦" |
| 通话中余额耗尽 | 立即停止，5秒倒计时，toast"对方信号不好，可以文字继续哦～" |
| 双方连续10秒无有效语音（信号层面异常） | 服务端强制挂断（与情绪停顿处理需做信号特征区分，见2.4.2冲突说明） |
| 通话中网络异常 | 先进入重连宽限窗口，超时未恢复才计为通话结束 |
| 危机关键词命中（仅限自伤/自杀） | 独立存储 + 展示资源卡片，不挂断不限制 |
| 危机检测范围外的风险内容 | ⚠️ 已知未覆盖，当前版本不处理 |
| 第三方隐私类内容 | 抽取阶段直接跳过，不生成不写入 |
| 未成年人 | 不做验证，用户自主声明18+ |
| 用户要求删除某次通话 | 不提供该入口，记忆已按来源标签分类，后续可批量处理 |
