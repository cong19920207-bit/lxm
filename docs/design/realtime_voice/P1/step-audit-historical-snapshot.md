## 附录：封禁 key 是什么（待确认，未冻结）

封禁 key 不是业务开关，而是 Redis 里用来标记「这个用户已被管理员禁用」的字符串名字。后台点禁用时往这个名字写入值；登录、Open API、以及未来的语音预检都去读同一个名字。名字写错，等于去空抽屉里查封禁状态。

| 来源 | 键名模板 | 例子（user_id=123） |
|---|---|---|
| PRD C109 / AC79 / 确认记录 V10-6 | `ban:{user_id}` | `ban:123` |
| 代码三处认证入口 | `user_banned:{user_id}` | `user_banned:123` |

代码现状：

- 写入：`backend/routers/admin/users.py:922`，`ban_key = f"user_banned:{user_id}"`
- 读取：`backend/utils/auth_middleware.py:35`、`backend/utils/open_api_auth.py:60`

如果语音预检按文档去读 `ban:123`，生产环境里这个键永远是空的，被封用户仍能发起通话，AC79 会假通过。两个选项：

1. 改文档，对齐代码的 `user_banned:{user_id}`（零迁移，需一条新 USER_DECISION）。
2. 照文档用 `ban:{user_id}`，并把三个认证入口一起迁移，必要时加双读兼容期（触碰主线鉴权，风险高）。

### 1.3 上一轮报告里需要修正的地方

#### 1.3.1 F-01 的论证站不住，但结论对

上轮说「草稿把 PRD 排在确认记录之前是根因」。这个说法有问题：PRD 自己的文档权威链（`:45-53`）就把 PRD 排第 1、确认记录排第 2，草稿是**照抄了 PRD**，不是凭空搞错。

正确的判据应该是证据数量和性质：observer 能否读正文，**四处权威表述说「能读」**（PRD C101、PRD §17.3 权限矩阵、DESIGN §权限矩阵 `:758`、确认记录 V9-2），**只有两处验收行说「不能读」**（PRD AC45 `:2281`、DESIGN `:1030`），而这两处都是 v2 遗留、在 v2.2 代码对齐修正时漏改的。所以证据唯一指向「observer 可读有效正文、不可导出」，`BLK-01` 确实是伪阻塞。

不过这是隐私边界。建议：结论按证据定，但把 AC45 的回写动作单独列出来让用户签字确认，而不是让实现者自行按优先级改掉一条隐私验收。

#### 1.3.2 F-07 的导出方法结论过强，应改为待裁决

上轮直接判「按优先级应以 GET 为目标」。但看原文：V9-5 和 C104 里的「导出是 GET」是**括注理由**（用来解释为什么方法级写总闸拦不住、必须显式挂 `deny_observer_export`），规范性要求只有「必须显式挂 `deny_observer_export`」这一句。真正的端点规范条目是 PRD `:1693`，写的是 `POST /api/admin/voice/calls/export`。DESIGN `:936` 干脆写「GET/POST 混合形态」。

这三处不能靠来源优先级唯一裁定，属于**需要用户裁决的项**，不能像上轮那样直接冻结成 GET。C88 那半（根 `docs/contract.md` 必须更新、草稿 RISK-03 `:67` 把它降级为「仅入口变化时更新」）则确凿成立。

#### 1.3.3 F-08 要升级：这不只是优先级问题，是安全缺陷

上轮只说「用代码基线覆盖用户决策不符合优先级」。实际风险更硬：PRD C109 `:385`、AC79 `:2351`、V10-6 `:269` 三处都写 `ban:{user_id}`，但代码里三个认证入口（`auth_middleware.py:35`、`open_api_auth.py:60`、`admin/users.py:922`）统一用 `user_banned:{user_id}`。

如果实现者「照 PRD 写」，语音预检会去读一个生产环境里永远为空的 key，**封禁校验静默失效**，AC79 表面通过、实际形同虚设。所以 RISK-02 不能留成「STEP-010 开工前的技术裁决」，必须升级为需要 `USER_DECISION` 的阻塞项，且两个选项的成本完全不同（改 PRD 一行 vs 迁移三个认证入口）。

#### 1.3.4 F-13 的行号引错了

上轮写「STEP-013 `:1243` 映射 C73」。`:1243` 是验收 ID 行，STEP-013 的详情段（`:1242`）**根本没有 C73**。真正的不自洽在三张总表之间，见下面 N-02。
