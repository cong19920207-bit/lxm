# “文档归纳”全局 Skill 设计

## 目标

创建一个可跨项目使用的本地全局 Skill，用于治理项目 `docs/` 目录内的需求与开发过程文档。Skill 以固定治理骨架约束文档类型、权威状态、生命周期、归档和校验方式，同时允许专题名称、文件数量和旧路径映射按项目现状适配。

用户展示名为“文档归纳”，机器名和目录名为 `document-synthesis`。

成功标准：

- Skill 只处理用户指定项目的 `docs/` 目录，不读取、分析或修改业务代码。
- 每次写入前先提交完整方案，只有用户明确确认后才能执行。
- 每次获准写入前保存涉及原文的不可变快照，Skill 不删除原始文档或快照。
- 执行后逐项对照原文，能够证明文件、章节、表格、代码块、链接和附件引用没有静默丢失。
- 日常任务只读取当前权威文档，默认排除草案、历史、归档和快照。
- 新项目采用固定默认路径；旧项目可通过 manifest 映射既有路径，新建内容向固定结构收敛。

## 范围

### 包含

- PRD 与需求说明。
- 需求确认、边界确认和决策记录。
- 开发步骤拆解与任务分解。
- 实施计划、里程碑计划和阶段方案。
- PRD 审查、步骤审查、方案审查和执行复盘。
- 契约草案、当前契约和历史契约。
- 开发进度、验收清单、测试指南和测试报告。
- 技术债、已知缺口和待确认事项。
- 文档索引、机器路由 manifest、文档关系和检索场景。
- 文档迁移、拆分、合并、版本快照、归档、恢复和原文校验。

### 排除

- 项目业务目录中的源代码、测试代码、脚本实现和数据库内容；不限制 Skill 自身用于文档清单、哈希、快照和校验的确定性脚本。
- 运行环境、部署环境、外部系统和在线服务。
- 根据业务代码反向生成或补全文档事实。
- 代码与文档实现一致性校验。
- 物理删除原始文档、历史版本、归档或快照。
- 未经用户确认的文档写入、移动、重命名、拆分、合并或归档。

当现有文档不能支撑某项内容时，Skill 只能标记 `planned`、`needs-review` 或 `needs-input`，并向用户说明缺失信息；不得用推测填充为已确认事实。

## 固定治理骨架

新项目默认使用以下结构；已有项目不强制一次性迁移，但必须在 manifest 中映射到相同逻辑槽位。

```text
docs/
├── INDEX.md
├── llm-manifest.json
├── design/
│   ├── README.md
│   └── <专题>/
│       ├── README.md
│       ├── prd/
│       ├── decisions/
│       ├── steps/
│       ├── plans/
│       ├── reviews/
│       └── validation/
├── contract.md
├── contract/
│   ├── current/
│   ├── drafts/
│   └── history/
├── progress/
├── testing/
│   ├── checklists/
│   ├── guides/
│   └── reports/
├── tech-debt.md
├── tech-debt/
│   ├── active/
│   └── archive/
└── archive/
    └── snapshots/
```

固定的是：

- `INDEX.md` 和 `llm-manifest.json` 两个治理入口。
- PRD、决策、步骤、计划、审查、验证、契约、进度和技术债等逻辑文档类型。
- `draft`、`current`、`history`、`archive` 和 `snapshot` 生命周期。
- 权威唯一性、默认读取边界、迁移门禁、归档规则和校验规则。
- 文档 ID、关系类型、原文追溯信息和检索场景字段。

自适应的是：

- 专题名称和专题数量。
- 某专题实际需要的文档类型和文件数量。
- 旧路径到固定逻辑槽位的映射。
- 文件语言、版本号和命名细节。
- 文档之间的依赖、扩展、替代和关联关系。

Skill 不得自行在 `docs/` 下增加新的一级治理类型。遇到无法归类的文档时，先在方案中提出扩展理由并等待用户确认。

## 文档内容契约

### PRD

- 背景与目标。
- 非目标。
- 用户或使用场景。
- 功能规则与业务规则。
- 边界、异常和冲突处理。
- 验收标准。
- 依赖、风险和未决问题。
- 版本与决策来源。

### 决策与确认记录

- 背景和待决问题。
- 场景与备选方案。
- 最终决策及原因。
- 被否决方案及原因。
- 影响范围和后续动作。
- 决策日期、状态和关联文档。

### 开发步骤

- 输入文档与前置条件。
- 每一步的目标、范围和产物。
- 步骤依赖和执行顺序。
- 禁止跨越的边界。
- 每一步的验证与完成条件。
- 对 PRD 条目的覆盖关系。

### 实施计划

- 目标和范围。
- 里程碑、阶段和交付物。
- 依赖关系和阻塞条件。
- 风险、回退和变更控制。
- 阶段验收标准。
- 进度更新方式。

### 审查文档

- 审查对象和基准文档。
- 覆盖、遗漏、冲突和歧义。
- 风险等级和影响。
- 建议、确认结果和剩余问题。
- 审查结论与后续动作。

### 验证与测试文档

- 验证范围和前置条件。
- 验证场景和步骤。
- 期望结果与实际结果。
- 失败证据和复测记录。
- 最终结论和未覆盖项。

### 技术债与已知缺口

- 唯一 ID、状态和优先级。
- 问题、影响和文档证据。
- 依赖、计划和完成条件。
- 验证证据与归档条件。

### 占位文档

- 状态必须是 `planned`、`needs-review` 或 `needs-input`。
- 明确当前已知内容和缺失内容。
- 明确需要用户提供的输入。
- 禁止把计划行为描述为当前已实现事实。

## 生命周期与权威规则

- `draft`：尚未确认，不能作为实施依据。
- `current`：当前唯一权威版本，可被日常任务读取。
- `history`：曾经生效但已被替代，保留版本演进信息。
- `archive`：已退出日常工作流的资料，只用于审计、恢复或专项核验。
- `snapshot`：写入前保存的不可变原文副本，不参与日常检索。

同一事实在同一作用域内只能有一个 `current` 权威来源。历史、归档和快照必须记录其当前替代文档，但不能与当前版本共同声明权威。

## 三阶段执行门禁

### 阶段一：只读分析与方案

Skill 必须先：

1. 读取项目指令和用户指定的文档边界。
2. 只盘点允许范围内的 `docs/` 文档。
3. 分类当前文档类型、状态、权威性和关系。
4. 识别缺失、重复、冲突、孤立、过期和路径偏差。
5. 输出目标目录树和逐文件处理表。
6. 列出拟新增、移动、重命名、拆分、合并、更新和归档的动作。
7. 给出快照范围、校验规则、风险和恢复方法。

此阶段禁止任何写入。方案必须明确说明“未执行”，并等待用户明确确认。

### 阶段二：确认后执行

收到用户明确确认后：

1. 再次核对本次获批范围，范围变化时返回阶段一。
2. 为每个将受影响的原始文档创建不可变快照。
3. 记录原路径、SHA-256、字节数、时间、目标路径和处理动作。
4. 创建已批准的目录和文档。
5. 执行已批准的移动、拆分、合并和内容整理。
6. 更新 `INDEX.md`、manifest、关系和默认读取边界。
7. 将被替代版本移入 `history` 或 `archive`，不执行物理删除。

若执行中发现方案外文件、内容冲突或无法确认的归属，立即停止相关动作并回到阶段一，不扩大授权范围。

### 阶段三：原文对照校验

执行完成后必须校验：

- 所有原始文件都存在于快照清单中。
- 快照文件的 SHA-256 与记录一致。
- 原始标题和章节全部存在唯一迁移去向。
- 普通段落、列表、表格、代码块、引用、链接和附件引用没有静默丢失。
- 拆分、合并后的正文可反向追溯到原始文件和原始章节。
- 当前权威文档唯一，草案、历史和归档不被误标为当前。
- 内部链接有效，INDEX 和 manifest 可以路由到当前文档。
- 日常检索场景不会加载草案、历史、归档或快照。

存在未覆盖、重复覆盖、哈希异常、链接断裂或权威冲突时，执行结果为失败。Skill 输出差异报告，不得宣称完成；利用快照恢复或提出修正方案后再次等待确认。

## 快照与归档

凡是 Skill 获准执行文档写入，都先对本次涉及的原始文档建立快照：

```text
docs/archive/snapshots/<YYYY-MM-DD-HHMMSS>/
├── SNAPSHOT.json
└── files/
```

`SNAPSHOT.json` 至少记录：

- 快照 ID、创建时间和触发任务摘要。
- 原始相对路径、SHA-256 和字节数。
- 计划动作和目标路径。
- 用户确认记录摘要。
- 校验状态和后续替代文档。

快照目录不可覆盖。Skill 不提供删除快照的流程。物理删除历史或快照不属于本 Skill 范围。

默认读取范围只包括 `INDEX.md`、manifest 中的 `current` 文档和当前任务必要的活跃文档。只有用户明确要求迁移校验、版本对比、恢复、生成新快照或专项审计时，才能读取 `drafts`、`history`、`archive` 或 `snapshots`。

## Skill 组成

```text
document-synthesis/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── document-model.md
│   ├── lifecycle-and-safety.md
│   └── validation-contract.md
├── assets/
│   └── templates/
└── scripts/
    ├── inventory_docs.py
    ├── snapshot_docs.py
    └── validate_migration.py
```

- `SKILL.md`：保持精简，定义范围、三阶段门禁和资源选择方式。
- `document-model.md`：保存固定目录槽位和各文档类型内容契约。
- `lifecycle-and-safety.md`：保存状态、权威、确认、快照、归档和停止条件。
- `validation-contract.md`：保存原文对照、覆盖、链接和检索校验规则。
- `assets/templates/`：保存新项目骨架及各类文档模板。
- 脚本只处理文件清单、哈希、快照和确定性校验，不读取或推断业务代码。

所有会修改项目文档的脚本默认 dry-run，并要求显式 `--apply`。即使使用 `--apply`，Skill 仍必须先取得当前会话中的方案确认，不能把命令参数视为用户授权替代品。

## 错误处理与停止条件

遇到以下情况立即停止相关执行：

- 目标路径超出获批 `docs/` 范围。
- 项目指令禁止读取或写入目标目录。
- 原始文件在方案确认后发生变化。
- 快照创建或哈希校验失败。
- 目标路径已有未纳入方案的文件。
- 文档归属、权威状态或合并规则存在歧义。
- 需要读取业务代码才能补全内容。
- 校验无法证明原文内容具有唯一去向。

停止时保留已经创建的快照，报告已完成动作和未执行动作；不得通过扩大扫描范围或猜测内容继续执行。

## Skill 验证策略

### 基线测试

在创建 Skill 前，以不加载 Skill 的独立场景验证常见失败行为，例如：

- 直接整理文档而未先给方案。
- 为补内容而读取业务代码。
- 移动文档后删除原文件且不保留快照。
- 只检查新目录存在，不与原文逐项核对。
- 日常任务误读历史或归档内容。

记录基线失败后，再编写最小规则修复这些行为。

### Skill 测试

- 触发测试：中文“文档归纳”、PRD 整理、开发文档迁移、docs 归档等请求能触发；普通代码修改不触发。
- 方案门禁测试：未确认时零写入，确认范围变化时重新出方案。
- 范围测试：只扫描指定 `docs/`，拒绝读取业务代码。
- 快照测试：不可覆盖、哈希一致、清单完整。
- 迁移测试：拆分、合并、重命名和旧路径映射均能通过原文覆盖校验。
- 权威测试：同一作用域出现多个 `current` 时失败。
- 检索测试：日常查询只加载当前文档，恢复查询才加载快照。
- 恢复测试：校验失败时可根据快照重建执行前文档状态。
- 通用性测试：至少覆盖已有复杂文档项目、简单单专题项目和只有少量 PRD 的空骨架项目。

## 验收标准

- Skill 展示名为“文档归纳”，机器名为 `document-synthesis`。
- Skill 文件符合 Agent Skills 命名、frontmatter 和目录规范。
- Skill 明确且实际遵守仅处理 `docs/` 文档的边界。
- 未确认方案时任何测试场景都不产生写入。
- 每次获准写入都有不可变快照、哈希清单和确认摘要。
- 迁移后能输出原文到目标文档的完整覆盖报告。
- 校验失败时不宣称成功，不删除原文，并能提出恢复或修正方案。
- 默认路由排除草案、历史、归档和快照。
- 脚本通过单元测试、代表性集成测试和 Skill 前向测试。
